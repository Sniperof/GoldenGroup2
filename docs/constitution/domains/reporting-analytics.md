# دستور الكيان: التقارير والمؤشرات (Reporting & Analytics Domain Constitution)

> **الحالة (Status):** Active Draft / Architectural Blueprint
> **التاريخ:** 2026-07-01
> **المرجع الأعلى لطبقة التقارير و KPIs والفلاتر في النظام.** يُعرّف البنية الموحّدة التي تُبنى عليها كل لوحات المؤشرات والتقارير القابلة للتصدير وفلاتر الجداول عبر كل أقسام Golden CRM.

## 0. التوصية المعمارية الجوهرية (The Spine)

**لا تُبنى ثلاث طبقات منفصلة (تقارير + KPIs + فلاتر). تُبنى طبقة تحليلات واحدة لها ثلاث واجهات استهلاك تتشارك «عقد نطاق» (Scope Contract) واحدًا.**

**السبب:** المتطلبات الثلاثة تقرأ نفس البيانات بنفس قواعد التقييد (زمن + فرع + إسناد). المنظومة تملك أصلًا محرك التقييد المطلوب — نطاقات الصلاحيات `GLOBAL / BRANCH / ASSIGNED`، و`X-Branch-Id`، وخطّاف `useBranchListScope`، وسياسات `authorize()`. بناء ثلاث طبقات منفصلة يكرّر منطق التقييد ثلاث مرّات ويخاطر بتسريب بيانات عبر الفروع. الطبقة الموحّدة تعيد استخدام الموجود وتضمن أن **بطاقة KPI والتقرير وجدول القائمة يُظهرون نفس الرقم دائمًا**.

```
                    ┌─────────────────────────────────────────┐
                    │   عقد النطاق الموحّد (Scope Contract)      │
                    │   الزمن + النطاق التنظيمي + فلاتر القسم     │
                    └─────────────────────────────────────────┘
                                      │
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
        ┌──────────┐           ┌──────────┐            ┌──────────┐
        │ KPI Cards│           │ التقارير  │            │  فلاتر   │
        │ (داشبورد)│           │ (تصدير)   │            │ الجداول  │
        └──────────┘           └──────────┘            └──────────┘
              └───────────────────────┼───────────────────────┘
                                      ▼
                    مصادر الحقائق المُقيّدة (Scoped Fact Sources)
       financial_movements · field_visits/visit_tasks · contact_targets
              contracts · open_tasks · installed_devices · candidates
```

## 1. الأساس المشترك (Cross-Cutting Foundation) — يُبنى مرّة واحدة

### 1.1 عقد النطاق (Scope Contract)

بُعدان إلزاميان + فلاتر اختيارية خاصة بكل قسم:

| البُعد | القيم | يُترجم إلى | يعيد استخدام |
|---|---|---|---|
| **الزمن (Time)** | اليوم / الأسبوع / الشهر / الربع / مدى مخصّص + مقارنة بالفترة السابقة (Δ) | `... BETWEEN :from AND :to` على عمود زمن المجال | — |
| **النطاق التنظيمي (Org Scope)** | (أ) كل الفروع ومقارنتها · (ب) فرع واحد · (ج) سجلاتي المُسندة | (أ)=`GLOBAL` · (ب)=`BRANCH` عبر `X-Branch-Id`/`BranchSwitcher` · (ج)=`ASSIGNED` عبر `useBranchListScope` | مستويات الصلاحية الثلاثة الموجودة حرفيًا |
| **فلاتر القسم (Domain Filters)** | تختلف لكل قسم (الحالة، النوع، الموظف، الموديل…) | شروط `WHERE` إضافية | تعريفات لكل قسم في §2 |

> **مبدأ:** البُعد التنظيمي يطابق نطاقات الصلاحية الثلاثة، فيُغذّي مفتاح النطاق نفسه الذي يُقيّد القوائم اليوم. أي مستخدم لا يستطيع رؤية مؤشر/تقرير على نطاق لا يملك صلاحية عرضه عليه — التقييد يُفرض في طبقة `authorize()`، لا في الواجهة.

### 1.2 مصادر الحقائق القانونية (Single Source per Metric)

لكل مؤشر **مصدر حقيقة واحد** يمنع تضارب الأرقام:

| المجال | جدول الحقيقة | عمود الزمن | عمود الفرع | ملاحظات |
|---|---|---|---|---|
| المال/التحصيل | `financial_movements` | `occurred_at` | `occurred_branch_id` | append-only؛ `kind ∈ charge/payment/refund/discount`؛ الرصيد = Σ(charge+refund)−Σ(payment+discount) |
| الزيارات | `field_visits` + `visit_tasks` | `scheduled_date` | `branch_id` | state machine: `scheduled→in_progress→ended→closed` |
| التسويق الهاتفي | `contact_targets` + سجلات الاتصال | `created_at`/الإسناد | عبر الزبون/الفرع | دورة الهدف: target→appointment→visit |
| العقود/المبيعات | `contracts` | `created_at` | `branch_id` / `service_branch_id` | `status`, `final_price`, `sale_subtype='definitive'` |
| الأجهزة المركّبة | `installed_devices` + الكفالات | حسب الحدث | فرع الخدمة | الصيانة الدورية + انتهاء الكفالة |
| الزبائن | `clients` + `client_rating_history` | `created_at` / `changed_at` | `branch_id` | الملكية عبر `client_assignments` (M2M) |
| الأسماء المقترحة | `candidates` | `created_at` | عبر الإحالة/الفرع | `status` ∈ New/Suggested/FollowUp/Contacted/Qualified/Junk |
| التوظيف | الشواغر/الطلبات/المقابلات | `created_at` | — | قمع التوظيف |

### 1.3 الطبقات التقنية (Reuse-first)

- **الباك-إند:** خدمة `metricsService` + نمط Endpoint موحّد:
  `GET /api/reports/:domain/:metric?from&to&scope&branchId&<domainFilters>`
  يمرّ عبر `authorize()` نفسها فيُفرَض النطاق تلقائيًا (لا تقييد يدوي مكرّر). كل metric دالة نقية (SQL aggregation) تقرأ من مصدر الحقيقة في §1.2.
- **الفرونت-إند — 4 مكوّنات مشتركة:**
  1. `<ScopeFilterBar>` — الزمن + النطاق التنظيمي (موحّد لكل صفحة تقارير/داشبورد).
  2. `<KpiCard>` — رقم + دلتا مقابل الفترة السابقة + سبارك-لاين. **يحلّ محل بطاقات `Dashboard.tsx` الحالية ذات الدلتا الوهمية (`+12%` ثابتة).**
  3. `<ReportView>` — جدول مُجمّع + تصدير Excel/CSV + رسم بياني.
  4. توسعة `SmartTable` بفلاتر عمودية قابلة للحفظ (Saved Views).

## 2. مصفوفة الأقسام (تقارير · KPIs · فلاتر)

> الترتيب حسب القيمة التشغيلية المتوقّعة. كل قسم يرث عقد النطاق في §1.1؛ الجدول أدناه يضيف ما يخصّه فقط.

### أ) التسويق الهاتفي والمواعيد (Telemarketing & Appointments)
- **تقارير:** إنتاجية المتصل (محاولات/تحويلات/مواعيد) · مسار جهات الاتصال (target→appointment→visit→contract) · أسباب الفشل · معدّل الالتزام بالموعد.
- **KPIs:** عدد المحاولات · معدّل التحويل لموعد % · مواعيد محقّقة/ملغاة · زمن البقاء في كل حالة.
- **فلاتر الجدول:** المتصل المسند · حالة الهدف · النتيجة · الفترة · الفرع · المنطقة.

### ب) التخطيط وعمل الفرع (Planning)
- **تقارير:** تغطية النطاقات (مخطّط/منفّذ) · توزيع المسارات على الفرق · فجوة الخطة مقابل التنفيذ.
- **KPIs:** نسبة تغطية المناطق % · مسارات بلا تعيين · أحياء غير مغطّاة · حمولة الفريق اليومية.
- **فلاتر:** المنطقة/خط السير · الفريق · اليوم · حالة الجدولة.

### ج) الزيارات الميدانية (Field Visits)
- **تقارير:** إنجاز الزيارات حسب الحالة · زمن الدورة · زيارات GPS خارج النطاق · نتائج الزيارة.
- **KPIs:** زيارات اليوم المكتملة % · متوسط مدة الزيارة · زيارات متأخرة · معدّل النتائج الناجحة.
- **فلاتر:** الحالة · الفريق/الفني المسند · النوع (تسويقية/طارئة/دورية) · المصدر (`field_initiated`/مخطّطة) · الفرع.

### د) العمليات والمهام (Operations & Tasks)
- **تقارير:** إنتاجية المهام حسب النوع · مهام متأخرة/SLA · قطع غيار مستهلكة · أسباب نتائج المهام (قوائم migr 345–349).
- **KPIs:** مهام مفتوحة/مكتملة لكل نوع · متوسط زمن الإغلاق · نسبة الإنجاز ضمن الموعد · مهام تحتاج متابعة.
- **فلاتر:** نوع المهمة · الحالة · المسند · الأولوية/الامتثال · الفرع · المدى الزمني.

### هـ) العقود والمبيعات (Contracts & Sales)
- **تقارير:** مبيعات حسب الفرع/البائع/نوع البيع · قمع البيع · عقود ملغاة وأسبابها (migr 339) · هدايا موعودة (migr 344).
- **KPIs:** عدد العقود · قيمة المبيعات (Σ`final_price`) · متوسط قيمة العقد · معدّل الإلغاء % · عقود مسوّدة عالقة.
- **فلاتر:** الحالة · نوع البيع · البائع/مالك البيع · الفرع · الفترة.

### و) المالية والتحصيل (Finance & Collections) — على `financial_movements`
- **تقارير:** أعمار الذمم (Aging) · محصّل مقابل مستحق · كشف حساب الزبون · تدفّق نقدي حسب `source_type`.
- **KPIs:** إجمالي المستحق (Σcharge−Σpayment) · المحصّل خلال الفترة · نسبة التحصيل % · ذمم متأخرة · مبالغ مرتجعة.
- **فلاتر:** نوع الحركة · المصدر · الفرع (`occurred_branch_id`) · الفترة.

### ز) الأجهزة المركّبة والصيانة (Installed Devices)
- **تقارير:** أعمار الأجهزة وكفالاتها · أجهزة مستحقة صيانة دورية · حركة الجهاز (ledger) · معدّل الأعطال حسب الموديل.
- **KPIs:** أجهزة مركّبة فعّالة · كفالات تنتهي قريبًا · أجهزة متأخرة عن الصيانة · أجهزة مفكوكة.
- **فلاتر:** الموديل · حالة الجهاز · حالة الكفالة · الفرع · المنطقة.

### ح) السجلات/الزبائن والأسماء المقترحة (CRM) — **قسم التعمّق، انظر §3**

### ط) التوظيف والموظفون (HR & Workforce)
- **تقارير:** قمع التوظيف (شاغر→طلب→مقابلة→قبول) · أداء الفرق (إنجاز/زيارات/مبيعات لكل موظف).
- **KPIs:** شواغر مفتوحة · طلبات قيد المعالجة · معدّل القبول · حمولة/إنتاجية الموظف.
- **فلاتر:** الشاغر · الحالة · القسم · الفرع.

## 3. التعمّق الأول: الزبائن والأسماء المقترحة (CRM Deep-Dive)

> نقطة البدء المعتمدة بعد الأساس (P0). مبنية على حقول `clients`, `candidates`, `client_rating_history`, `client_assignments`, `referral_sheets`, `direct_suggestions` الفعلية. كل صف widget أدناه يحقّق عقد §8.2 كاملًا (سؤال/صيغة/مصدر واحد/حبيبة/صلاحية/غاية) ولا يدخل الكتالوج إلا ما اجتاز اختبار §8.3 الثلاثي: غير مكرّر + يخدم قرارًا أو سير عمل أو إنجاز فريق + مصدره واحد.
>
> **ملاحظة تسمية:** الشاشة التي يسمّيها المستخدمون «سجلات الأسماء المقترحة» في الشريط الجانبي (`/candidates`) هي جدول `candidates` نفسه. أي widget هنا بعنوان «الأسماء المقترحة» يقصد هذا الجدول.

### 3.1 مصادر الحقيقة وأعمدتها

| المؤشر/التقرير | الجدول | الأعمدة المفتاحية |
|---|---|---|

| التزام الزبون وتطوّره | `client_rating_history` | `new_rating`, `old_rating`, `changed_at` (`Committed/NotCommitted/Undefined`) |

| — | فترة الإنشاء | `created_at` | مدى تاريخ | عام |

**الإجمالي: ١ حقل بحث + ١١ فلترًا (بعدّ فترة الإنشاء) = ١٢ عنصر تصفية.**

> **ثلاثة أدوار مستقلّة على اللائحة الواحدة (#2/#3/#4):** الجامع الفعلي (مَن يجمع الأسماء ميدانيًا) ≠ المُراجِع المُسنَد (مَن يراجع النتيجة رسميًا) ≠ المنشئ (مَن أنشأ سجل اللائحة بالنظام، وقد يكون مشرفًا لا علاقة له بالجمع أو المراجعة). الكود الحالي يملك الأعمدة الخام الثلاثة (`owner_user_id`, `assigned_hr_user_id`, `created_by`) لكنه يُظهر اسمًا واحدًا مُدمَجًا فقط — لا فلتر مستقلّ لأيٍّ منها اليوم.

> **شرط تصميمي سابق للفلترين #2/#3:** الكود الحالي يعرض حقلًا واحدًا فقط `assignedHrUserName` وهو `COALESCE(assigned_hr_user_id, team_responsible_user_id, owner_user_id)` — أي مطابقة نصية على أول اسم متاح من ثلاثة أدوار مختلفة. لا يمكن بناء فلترين منفصلين (#2 و#3) دون تعديل الاستجابة لإرجاع الحقلين الخام كل على حدة (كلاهما متاح فعليًا في قاعدة البيانات، لا ينقص شيء سوى فصلهما في الاستجابة والواجهة). راجع `docs/analysis/candidates-referral-sheets-filters-audit.md §2.2`.

### 3.6 تقرير مركّب: القمع الكامل من ترشيح إلى عقد (Cross-Entity Funnel Report)

تقرير واحد (لا widget، بل `<ReportView>` من §1.3) يربط ثلاث مراحل بمصدر واحد لكل مرحلة، دون ازدواج حساب:
`referral_sheets/direct_suggestions (توليد الاسم) → candidates.status (التأهيل) → clients.is_candidate + converted_to_lead_id (التحويل) → contracts (البيع الفعلي، §2.هـ)`.
الغاية: قرار استراتيجي واحد — أين نخسر الفرص فعليًا: عند التوليد، أم التأهيل، أم الإغلاق؟ يُبنى بعد استقرار Tier 1 من §3.2/§3.4.

### 3.7 التوزيع الجغرافي وخط السير (Geo & Route Rollup) — يشمل الزبائن والمرشّحين معًا

> بُعد أفقي يُطبَّق على القسمين معًا، لا widget بذاته بل **تقرير `<ReportView>` واحد قابل للتبديل** بين «الزبائن» و«الأسماء المقترحة» بنفس شكل الجدول.

| # | التقرير | الصيغة | الحبيبة | الغاية | نوع الرسم |
|---|---|---|---|---|---|
| 1 | `clients.by_route` | `COUNT(*) GROUP BY route_id` عبر `route_points` (مطابقة `neighborhood::int = route_points.geo_unit_id` حيث `level=4`) | لكل خط سير × نطاق | قرار: أي خطوط السير تغطّي أعلى كثافة زبائن فعليًا | Bar أفقي مرتّب + جدول تفصيلي |
| 2 | `candidates.by_route` | `COUNT(*) GROUP BY route_id` عبر `route_points.geo_unit_id = candidates.geo_unit_id`، مع `conversion_rate` لكل خط | لكل خط سير × نطاق | قرار: أي خطوط السير تُنتج مرشّحين قابلين للتحويل فعليًا، لا فقط عددًا | Bar مزدوج (عدد + معدّل تحويل) |
| 3 | `clients.by_geo_area` / `candidates.by_geo_area` | `COUNT(*) GROUP BY governorate/district/neighborhood` (زبائن) أو `geo_unit_id` (مرشّحون) | لكل مستوى جغرافي × نطاق | قرار: تخطيط تغطية على مستوى أدق من خط السير (حي/منطقة) | Bar أفقي مرتّب (Top N)، ويطابق `clients.top_geo_areas` #8 §3.2 |

> **لماذا خط السير مهم بالتحديد:** خط السير هو وحدة التخطيط الميداني الفعلية (يُسنَد لفريق، له جدول زيارات). معرفة كثافة الزبائن/المرشّحين *لكل خط سير* — لا فقط لكل حي — تربط مؤشرات CRM مباشرة بقرار «أين نرسل الفريق التالي» (يتقاطع مع دومين Planning §2.ب).

### 3.8 أداء الملكية حسب الموظف/المشرف (Ownership Performance by Employee)

> يجيب مباشرة عن: «ماذا يملك ويحقّق كل موظف من السجلات المسندة إليه، ضمن ما تسمح به صلاحيته؟» — مختلف عن `referral_sheets.team_quality_leaderboard` (#8 §3.4) الذي يقيس *جودة أوراق الإحالة* تحديدًا، لا الملكية الخام.

| # | Widget key | العنوان | الصيغة | الحبيبة | الغاية | نوع الرسم | الأولوية |
|---|---|---|---|---|---|---|---|
| 1 | `clients.ownership_breakdown` | الزبائن المملوكون لكل موظف | `COUNT(*) GROUP BY client_assignments.hr_user_id` + نسبة `Committed` لكل موظف | لكل نطاق × موظف | إنجاز فريق: حجم وجودة محفظة كل موظف مسؤول عنها | Bar أفقي مرتّب (Leaderboard) | ⏳ Tier 1 |
| 2 | `candidates.ownership_breakdown` | المرشّحون المملوكون لكل موظف | `COUNT(*)`, `COUNT(converted_to_lead_id NOT NULL)` `GROUP BY owner_user_id` ضمن الفترة | لكل فترة/نطاق × موظف | إنجاز فريق: مَن يحوّل مرشّحيه فعليًا لا فقط يجمعهم | Bar مزدوج (عدد + معدّل تحويل) | ⏳ Tier 1 |

> **ملاحظة نطاق:** هذان التقريران مفيدان فعليًا لصاحب اتساع `BRANCH`/`GLOBAL` (مشرف/مدير يقارن بين أعضاء فريقه). لصاحب اتساع `ASSIGNED` تنهار المجموعة تلقائيًا لصف واحد (نفسه) بحكم تقاطع §8.1 — سلوك آمن ومتوقَّع، لا استثناء أمني، لكنه يُفرِغ الـ widget من قيمته كـ«مقارنة»؛ لذلك الأنسب تصنيفه بصريًا كبطاقة «أدائي الشخصي» عند عرضه لمستخدم `ASSIGNED`.

### 3.9 دليل اختيار نوع الرسم البياني (Chart-Type Decision Guide)

| طبيعة المؤشر | نوع الرسم الموصى به | مثال من أعلاه |
|---|---|---|
| رقم واحد + اتجاهه عبر الزمن | رقم + Sparkline (ضمن `<KpiCard>`) | زبائن جدد، معدّل التحويل |
| توزيع مراحل متتالية (قمع) | **Funnel Chart** | `candidates.stage_funnel` |
| حصص فئات قليلة (٢–٤) من كل | Donut/Pie | نسبة الالتزام، التصنيف LEAD/OP/FOP، نوع المُحيل/الوسيط |
| ترتيب فئات/أفراد بعدد كبير نسبيًا | Bar أفقي مرتّب تنازليًا (Top N) | القنوات، المناطق، خطوط السير، Leaderboard الفرق/الموظفين |
| مقارنة عدد مقابل معدّل لكل فئة | Bar مزدوج (محورين) | `candidates.by_route`، `candidates.ownership_breakdown` |

| حاجة تدقيق/متابعة سجلات فردية | جدول تفصيلي (`<ReportView>`) خلف الرقم | زبائن بلا نشاط، أوراق دون الهدف |

### 3.10 ثغرات وقيود تؤثّر على دقّة المؤشرات

- **تضارب مسمّى حالة المرشّح** (`New` في الداتابيز مقابل `Prospect` في طبقة التطبيق) — يجب توحيده قبل بناء قمع التحويل (#2 §3.4) وإلا اختلّت العدّة (راجع `candidates.md §9`).
- **غياب ترانزأكشن تحويل المرشّح لزبون** — قد يُنشأ زبون دون تحديث `converted_to_lead_id`، فيُحتسب التحويل ناقصًا (#3 §3.4). يُعالج كشرط دقّة قبل اعتماد KPI «معدّل التحويل».
- **غياب سجل تاريخي لحالة المرشّح** (`candidate_status_history`) — يمنع حساب «متوسط زمن البقاء بكل مرحلة» (آخر صف §3.4) بدقّة؛ `client_rating_history` (migr 343) يقدّم نموذجًا جاهزًا للتكرار على `candidates`.
- **`direct_suggestions` غير موحّد مع `candidates`** — مسار منفصل (راجع مهمة الدستور المعلّقة «بيانات الأسماء المقترحة ولوائح الأسماء» في `INDEX.md`)؛ لذلك قمعه (#10 §3.4) يُحتسب مستقلًا لا كجزء من قمع `candidates.stage_funnel` حتى تُحسم مهمة التوحيد.
- **تعريف «النشاط» لمؤشر #9 §3.2 (`clients.inactive_count`) مفتوح** — أي نافذة زمنية وأي أحداث (زيارة/مهمة/عقد/اتصال) تُحتسب؟ محجوب حتى يُحسم (قرار §5.1).
- **مستوى `candidates.geo_unit_id` غير مؤكَّد** — لا عمود `level` مرافق (خلافًا لـ `route_points`)؛ افتراضنا أنه يُلتقَط عادة على مستوى الحي (`level=4`) مثل خطوط السير، لكن يلزم تحقّق فعلي على بيانات الإنتاج قبل اعتماد `candidates.by_route` (§3.7 #2).
- **`clients.governorate/district/neighborhood` مخزّنة كـ `VARCHAR`** لا `INTEGER` (خلافًا لـ `geo_units.id` و`route_points.geo_unit_id`) — أي join جغرافي (`by_route`, `by_geo_area`) يتطلّب `cast` صريحًا؛ نفس الملاحظة الموثّقة أصلًا في `clients.md`.
- **`occupation` مخزّن كنص لكنه يُقرأ تشغيلياً من قائمة النظام `occupation` المشتركة للزبائن والأسماء المقترحة (قرار 2026-07-29).** الفجوة المتبقية هي فرض المطابقة خادمياً وتوحيد resolver للحالة الفعالة/التاريخية؛ وإلا يمكن لطلب ملفق أن يعيد إدخال قيم حرة ويشتّت مؤشر `clients.top_occupations`.

## 5. القرارات والثغرات المفتوحة

3. **ترانزأكشن تحويل المرشّح** (§3.10) — شرط دقّة لـ KPI `candidates.conversion_rate` (§3.4 #3).
4. **صلاحيات التقارير** — هل نشتقّ صلاحية عرض كل مؤشر/تقرير من صلاحية عرض القائمة المقابلة (مثل `clients.view_list`) أم نُنشئ مفاتيح `reports.*` مستقلة؟ التوصية: الاشتقاق أولًا لتجنّب تضخّم شجرة الصلاحيات.
5. **تطبيع بصمة النطاق للكاش (`scope_signature`)** — تعريف دقيق لكيفية تحويل الـ presets الزمنية النسبية (اليوم/الشهر…) إلى مفتاح كاش مستقرّ دون انفجار عدد النسخ (§7.5). يلزم حسمه قبل بناء جدول `metric_cache`.
6. **إنشاء `candidate_status_history`** — جدول تاريخي نظير `client_rating_history` (migr 343) لتسجيل كل تغيّر حالة مرشّح بتاريخه؛ شرط بناء ضروري لمؤشر `candidates.avg_time_in_stage` (§3.4، الصف الأخير) وأي تحليل زمني لاحق للقمع.
7. **توحيد `direct_suggestions` مع `candidates`** — مرتبط بمهمة الدستور المعلّقة «بيانات الأسماء المقترحة ولوائح الأسماء» (`INDEX.md`)؛ إلى حين حسمها يبقى `direct_suggestions.mini_funnel` (§3.4 #10) مؤشرًا مستقلًا لا يُدمج مع `candidates.stage_funnel`.
8. **التحقّق من مستوى `candidates.geo_unit_id`** (§3.10) — تأكيد أنه يُلتقَط دومًا على مستوى الحي (`level=4`) قبل اعتماد `candidates.by_route` (§3.7 #2).
9. **إكمال إنفاذ عقد `occupation` الموحّد** (§3.10) — الواجهة تقرأ حالياً من قائمة النظام المشتركة؛ المتبقي هو resolver/validation خادمي واحد للزبائن والأسماء المقترحة، مع إبقاء القيم التاريخية المعطلة مقروءة، قبل اعتماد `clients.top_occupations` (§3.2 #11).

## 6. الداشبورد العام القابل للتخصيص (Customizable Widget Dashboard)

### 6.1 المبدأ — قشرة Widgets رقيقة فوق طبقة المؤشرات
الداشبورد ليس مكوّنًا جديدًا، بل **طبقة تخطيط نحيفة** فوق مصفوفة §2. كل widget = مؤشر/تقرير من المصفوفة يُرسم داخل `<KpiCard>`/`<ReportView>` ويرث `<ScopeFilterBar>`. الخطر الذي نتجنّبه: أن يتضخّم إطار التخصيص (سحب/تحجيم/شبكات) ويبتلع الوقت قبل وجود محتوى — لذلك نبدأ نحيفًا.

واجهة العرض تُقسّم الكتالوج إلى أقسام (`summary`/`clients`/`candidates`/`name-lists`). لا يُركَّب مكوّن widget ولا يُرسل طلب بياناته إلا بعد فتح قسمه؛ القسم النشط محفوظ في query parameter باسم `section` ليدعم الروابط المباشرة والرجوع في المتصفح. شريط الزمن/الفرع عام، بينما ظهور الأقسام نفسها مشتق من صلاحيات widgets المتاحة للمستخدم.

### 6.2 عمق التخصيص (MVP المعتمد)
- إضافة/حذف widgets من كتالوج + **إعادة ترتيب بالسحب (drag-reorder)** عبر `@dnd-kit` (أخفّ من `react-grid-layout`).
- **محفوظ لكل مستخدم**، مع **تخطيط افتراضي مشتقّ من الدور** (لا داشبورد فارغ للمستخدم الجديد).
- **مؤجّل بوضوح:** التحجيم الحرّ والشبكة المرنة (resize grid) — يُضاف لاحقًا دون كسر النموذج.

### 6.3 نموذج البيانات
عمود `user_dashboard_layout JSONB` على تفضيلات المستخدم (لا جدول صف-لكل-widget — غير ضروري للترتيب/الإضافة):
```json
[ { "key": "crm.new_clients",      "size": "sm", "scope": null },
  { "key": "crm.conversion_rate",  "size": "sm", "scope": null },
  { "key": "crm.candidate_funnel", "size": "lg", "scope": { "branchId": 3 } } ]
```
`scope: null` = يتبع شريط النطاق العام؛ كائن = نطاق مثبّت (Pin) لهذا الـ widget وحده.

### 6.4 كتالوج الـ Widgets (Registry — فرونت)
مصفوفة مركزية واحدة، كل عنصر:
```ts
{ key, titleAr, permission, department, defaultSize, component }
```
- الكتالوج يُفلتر بالصلاحية (`hasPermission(permission)`): لا يرى المستخدم — حتى عند التخصيص الذاتي — إلا widgets يملك صلاحية عرض مصدرها.
- دفاع بطبقتين: الـ endpoint يفرض النطاق ثانيةً عبر `authorize()`، فلا تسريب بيانات عبر تخصيص يدوي.

### 6.5 المكوّنات
| المكوّن | الدور |
|---|---|
| `<DashboardPage>` | تحميل التخطيط، رسم الشبكة، شريط النطاق، زر «+ إضافة widget» |
| `<ScopeFilterBar>` | زمن/فرع/مُسند — يطبّق على كل الـ widgets |
| `<WidgetFrame>` | إطار: عنوان + مقبض سحب + حذف + (Pin نطاق) + «آخر تحديث» + زر تحديث |
| `<WidgetCatalogModal>` | الـ widgets المسموحة مجمّعة حسب القسم |
| `<KpiCard>` / `<ReportView>` | محتوى الـ widget الفعلي |

### 6.6 التخطيط الافتراضي لكل دور
خريطة `role → [widget_keys]` تُستخدم عند غياب تخطيط محفوظ، ثم يُسمح للمستخدم بالتعديل والحفظ.

### 6.7 خطوات البناء (P0 + أول widgets CRM)
1. Migration: `user_dashboard_layout JSONB` + جدول الكاش (§7.2).
2. Endpoints: `GET/PUT /api/me/dashboard-layout` + `GET /api/reports/:domain/:metric` + `POST .../refresh`.
3. مكوّنات الأساس: `ScopeFilterBar` + `KpiCard` + `WidgetFrame` + هيكل الـ registry.
4. `DashboardPage` بترتيب dnd + كتالوج + حفظ.
5. أول 3–4 widgets CRM موصولة بـ endpoints حقيقية (زبائن جدد · معدّل التحويل · نسبة الملتزمين · مؤهّلون لم يُحوّلوا) — **تستبدل الدلتا الوهمية في `Dashboard.tsx`**.

## 7. معيار جلب البيانات والتحديث (Data Fetch & Caching Standard) — **إلزامي**

> هدف هذا المعيار: ألّا يضغط الداشبورد على الداتابيز/السيرفر بجلب بيانات كبيرة باستمرار. **البيانات تُجلب فقط للـ widgets المستخدمة فعليًا، وتُخدم من كاش يُحدَّث كل فترة يحددها الأدمن أو يدويًا.**

### 7.1 الجلب عند الطلب فقط (On-Demand Only)
- لا تُحسب مؤشرات أي widget **غير مُضاف** إلى تخطيط مستخدم. الواجهة تطلب فقط widgets التخطيط الفعّال (ويفضَّل الظاهرة على الشاشة).
- لا precompute شامل لكل المؤشرات؛ الحساب مدفوع بالاستخدام الحقيقي.

### 7.2 كاش المؤشرات على الخادم (Server-Side Metric Cache)
جدول `metric_cache`:
```
metric_key · scope_signature · value JSONB · computed_at · computed_by
```
- `scope_signature` = بصمة مُطبَّعة من (المؤشر + الزمن + الفرع/الإسناد) لتمييز نسخ الكاش.
- طلب الـ widget يُخدم من الكاش مباشرةً دون لمس جداول الحقيقة.

### 7.3 فترة تحديث يحددها الأدمن + تحديث يدوي
- إعداد `dashboard_metric_refresh_hours` (كل X ساعة) عبر `/api/system-settings` (يعيد استخدام صلاحية `settings.manage`).
- منطق الخدمة: إذا `now − computed_at < interval` → يُعاد الكاش؛ غير ذلك → يُعاد الحساب ويُحدَّث الكاش.
- **تحديث يدوي:** زر «تحديث» على كل widget → `POST /api/reports/:domain/:metric/refresh` يفرض إعادة الحساب فورًا (محكوم بنفس صلاحية العرض).

### 7.4 وظيفة التحديث المجدولة تمسّ المستخدَم فقط
وظيفة دورية (cron) تمرّ على **المجموعة الفريدة `(metric_key, scope_signature)` المستخرجة من كل تخطيطات المستخدمين المحفوظة** فتُعيد حساب ما هو مستخدَم فعليًا فقط — لا حساب لمؤشر/نطاق لا يستعمله أحد. هذا هو التطبيق العملي لمبدأ §7.1 على مستوى الخادم.

### 7.5 ضبط تضخّم الكاش (Cardinality Control)
- الكاش يُكتب فقط للنطاقات **الخشنة** (لكل فرع / كل الفروع) والـ presets الزمنية القياسية (اليوم/الأسبوع/الشهر/الربع).
- المدى الزمني المخصّص (custom range) والاستعلامات النادرة تُحسب **حيًّا** مع حدّ معدّل (rate-limit) ولا تُكتب في الكاش، منعًا لانفجار عدد النسخ.

### 7.6 عرض الحداثة (Freshness UX)
كل widget يعرض «آخر تحديث: HH:MM» (من `computed_at`) + زر تحديث يدوي، ليعرف المستخدم أن الرقم مُخزَّن لا لحظيًّا. (تحسين لاحق اختياري: stale-while-revalidate.)

## 8. حوكمة الـ Widgets: الصلاحيات وقيمة المعلومة (Widget Governance) — **إلزامي**

> مبدأ حاكم: لكل widget جمهورٌ محدّد بالصلاحية لا يتجاوزه، وخلف كل مؤشر/KPI/مخطط **معلومة واحدة غير مكرّرة تخدم قرارًا أو متابعة سير عمل أو قياس إنجاز فريق**. ما لا يحقق ذلك لا يدخل الكتالوج.

### 8.1 التنظيم على مستويات الصلاحية (Permission-Tiered Access)
وصول الـ widget محكوم ببوابتين مستقلّتين:
1. **بوابة الرؤية (Visibility):** مفتاح الصلاحية — هل يحقّ له رؤية هذا المؤشر أصلًا؟
2. **بوابة الاتساع (Breadth):** النطاق الذي يُعرض به = **تقاطع** `permission.allowed_scopes` ∩ النطاقات الممنوحة للمستخدم لتلك الصلاحية. **يُمنع اختراع نطاقات في الـ registry** — تُقرأ من الصلاحية نفسها.

| الطبقة | الجمهور | النطاق | مثال widget |
|---|---|---|---|
| تنفيذية | إدارة عليا (يملك `GLOBAL`) | كل الفروع + مقارنة | مبيعات كل الفروع |
| فرعية | مدير فرع (يملك `BRANCH`) | فرع واحد | مبيعات فرعي |
| تشغيلية | مشرف/فني/متصل (يملك `ASSIGNED`) | سجلاتي/فريقي فقط | مهامي المتأخرة |

**قواعد:**
- المؤشر الواحد قد يظهر في عدّة طبقات، لكن كل مستخدم يراه **فقط بالاتساع الذي يسمح به منحُه**.
- إن لم يملك المستخدم أيًّا من نطاقات المؤشر المسموحة → يختفي من الكتالوج (لا يقدر حتى على إضافته).
- `<ScopeFilterBar>` يعرض فقط مستويات النطاق التي يملكها المستخدم لتلك الصلاحية — فلا يمكنه اختيار اتساع لا يحقّه.

### 8.2 عقد تعريف الـ Widget (Widget Definition Contract) — شرط دخول الكتالوج
يوسّع الشكل المختصر في §6.4. **لا يُسجَّل widget دون تصريح كامل بهذه الحقول:**

| الحقل | المعنى |
|---|---|
| `key` | معرّف فريد |
| `question` | القرار/السؤال الذي يجيب عنه — **إلزامي؛ بلا قرار = يُرفض** |
| `formula` | الصيغة الدقيقة للحساب |
| `source` | جدول الحقيقة + الأعمدة (§1.2) — **مصدر واحد** |
| `grain` | حبيبة القياس (لكل زبون/مهمة/يوم/فرع…) |
| `permission` + `allowedScopes` | بوابة الرؤية + الاتساع (تُقرأ من الصلاحية) |
| `audience` | الطبقة (تنفيذية/فرعية/تشغيلية) |

### 8.3 قاعدة عدم التكرار (Single-Canonical Rule)
- **مؤشر قانوني واحد لكل (مفهوم × حبيبة).** أي «نسخة» أخرى = تغيير نطاق/فلتر للمؤشر نفسه، لا مؤشر جديد.
- يُمنع حساب الرقم نفسه بطريقتين (تأكيد §1.2: مصدر حقيقة واحد).
- **مراجعة إدخال إلزامية** قبل تسجيل أي widget — يجب أن يحقّق الثلاثة معًا:
  1. غير مكرّر لمؤشر قائم.
  2. يخدم قرارًا إداريًا أو متابعة سير عمل أو قياس إنجاز فريق.
  3. مصدره واحد وصيغته محدّدة.
  ما لا يحقّق الثلاثة لا يدخل الكتالوج (لا مؤشرات استعراضية / vanity metrics).

### 8.4 تتبّع القيمة إلى الغاية (Decision Traceability)
كل widget يُصنَّف بغايته الصريحة: **قرار إداري / متابعة سير عمل / قياس إنجاز فريق**. يظهر التصنيف في توثيق الكتالوج، فيُمكن تدقيق أن الداشبورد بأكمله موجَّه لغاية — وأي widget بلا غاية واضحة يُزال.

## 9. معيار هندسة التقرير الجدولي لأي Module — **إلزامي**

> هذا القسم هو البنية الأساسية الملزمة لبناء أي تقرير جدولي في أي قسم من Golden CRM. لا يكفي إنتاج SQL يعيد صفوفًا؛ التقرير منتج بيانات كامل له سؤال إداري، وحبيبة صف، ومصادر حقيقة، وعقد زمن، وسياسة وصول، وفلاتر، ولقطة توليد، وعقد تصدير، وأدلة اختبار.

### 9.1 حدود المعيار والمبادئ الحاكمة

- ينطبق على تقارير ملفات العمل، والأداء، والموارد البشرية، والخدمة، والعمل اليومي، وأي مجموعة لاحقة.
- الافتراض هو **التوليد اليدوي عند الطلب**. لا يوجد توليد تلقائي أو تحديث صامت للتقرير ما لم ينص عقد تقرير معتمد على غير ذلك.
- كل نسخة مولّدة هي **Snapshot ثابتة** تحمل `generatedAt` وهوية من ولّدها والفلاتر والنطاق الفعلي. التصدير له `exportedAt` مستقل ولا يعيد توليد البيانات.
- الخادم هو المسؤول عن الصلاحيات، والنطاق، وصحة الفلاتر، وحبيبة الصف، والعدد الكلي. الواجهة ليست حدًا أمنيًا.
- لا يُقرأ التاريخ الماضي من الحالة الحالية. التقرير التاريخي يحتاج سجل أحداث مكتملًا يثبت الانتقالات. وجود Activity Log لوحده لا يكفي حتى تُدقّق تغطيته وترتيبه وعدم قابلية أحداثه للحذف أو الاستبدال.
- لكل تقرير **سؤال إداري واحد معرّف**. الأعمدة التي لا تخدم هذا السؤال تُسقط أو تنقل لتقرير تفصيلي مستقل.

### 9.2 دورة حياة التقرير وبوابات المرور

يمر أي تقرير بست بوابات مترابطة. لا يبدأ تنفيذ البوابة اللاحقة قبل إغلاق مخرجات السابقة:

| البوابة | الغاية | المخرج الإلزامي | شرط المرور |
|---|---|---|---|
| **G0 — الطلب** | فهم القرار الذي سيخدمه التقرير | عنوان، مجموعة، جمهور، سؤال إداري، قائمة أعمدة أولية | كل عمود له معنى واستخدام متفق عليه |
| **G1 — التحليل** | إثبات أن النظام يملك البيانات والتاريخ اللازمين | خريطة مصادر، حبيبة صف، عقد زمن، عقد ملكية/إسناد، قائمة فجوات | كل حقل مصنّف: متاح/مشتق/غير ممكن/يحتاج قرارًا |
| **G2 — التصميم** | تثبيت العقد قبل الكود | Report Definition كامل + عقد API + سياسة وصول + فلاتر + استراتيجية SQL | لا توجد دلالة مجهولة أو نطاق أو حالة زمنية ضمنية |
| **G3 — التنفيذ** | بناء شريحة عمودية كاملة | registry + policy + service/query + routes + UI + snapshot + export | كل طبقة تستهلك نفس العقد ولا تعيد اختراع القرار |
| **G4 — التقييم** | مقارنة النتيجة بالسؤال وبيانات مرجعية | عينات مدقّقة، تفسير الفروق، مراجعة UX/Writing، قياس أداء | الأرقام قابلة للتفسير والفروق ليست صامتة |
| **G5 — القبول** | إثابت الصحة والأمان والتصدير | مصفوفة اختبار ناجحة + أدلة تشغيل على DB ممثلة | اجتياز الاختبارات السلبية والإيجابية ومطابقة Excel للقطة |

### 9.3 عقد تعريف التقرير (Report Definition Contract)

لا يدخل أي تقرير إلى الكتالوج من دون الحقول الآتية:

| الحقل | القاعدة |
|---|---|
| `key` | معرّف ثابت لا يعتمد على عنوان الواجهة، بنمط `<group>.<report>` |
| `groupKey` | مجموعة التقرير |
| `title` / `description` | صياغة عربية تشغيلية تستخدم مصطلحات المشروع، لا قيم DB الخام |
| `question` | السؤال الإداري الذي يجيب عنه |
| `audience` | إدارة عليا / فرع / فريق / موظف، مع الفصل بين الجمهور والنطاق الأمني |
| `grain` | المعنى الدقيق لكل صف: جهاز، زبون، زيارة، موظف×منطقة، مهمة... |
| `subject` | الكيان الذي يُطبّق عليه قرار الصلاحية، وحقل فرعه، وعلاقة إسناده إن وجدت |
| `timeMode` | `current_snapshot` أو `event_history` أو `period_activity` |
| `timeSemantics` | عمود الزمن لكل مقياس، وهل النطاق الزمني مطلوب أم غير مسموح |
| `sources` | جداول الحقيقة، المفاتيح، شروط الانضمام، ومصدر كل عمود |
| `columns` | مفتاح، عنوان، نوع، عرض، دلالة، قاعدة القيمة الفارغة، شرط الظهور، وهل يقبل الفرز |
| `filters` | فلاتر التقرير فقط، مع نوع كل فلتر ومصدر خياراته وقاعدة تحققه |
| `viewPermission` / `exportPermission` | بوابتان مستقلتان |
| `supportedScopes` | النطاقات التي للتقرير subject قابل لإثاتها فعليًا |
| `defaultSort` | فرز حتمي ومستقر، ينتهي بمفتاح فريد لمنع تذبذب الصفحات |
| `freshness` | سياسة التوليد واللقطة، مع `generatedAt` و`generatedBy` |
| `export` | الصيغ، الأعمدة، الأنواع، حدود الحجم، وقواعد الحماية |
| `guide` | شرح الأعمدة والحسابات بمصطلحات الواجهة |

### 9.4 تحليل البيانات قبل التصميم

#### 9.4.1 خريطة الحقل إلى الحقيقة

لكل عمود مطلوب يُسجّل:

1. الكيان الذي يصفه.
2. الجدول والعمود القانونيان، أو معادلة الاشتقاق.
3. مفتاح الربط الذي يثبت أن السجل يخص حبيبة الصف.
4. دلالة الحالة والقيمة الفارغة.
5. الترجمة العربية المعتمدة.
6. تصنيف الثقة: **مباشر**، **مشتق حتمي**، **تقريبي**، أو **غير ممكن حاليًا**. لا يدخل حقل تقريبي دون إظهار قيده للمستخدم.

#### 9.4.2 تثبيت حبيبة الصف

- يُكتب اختبار لغوي: «كل صف يمثل ...».
- يُحدّد المفتاح الفريد للحبيبة، ويجب أن يبقى `COUNT(rows) = COUNT(DISTINCT grain_key)` بعد كل الربطات.
- العلاقات one-to-many لا ترتبط مباشرة بالصف الرئيسي. تُختزل أولًا إلى صف واحد بـ `LATERAL` أو CTE مجمّع أو `DISTINCT ON` مع قاعدة حسم مستقرة.
- «آخر» لا تعني `MAX(id)` تلقائيًا؛ يجب تعريف عمود الزمن وقاعدة التعادل، مثل `ORDER BY executed_at DESC, id DESC`.

#### 9.4.3 عقد الزمن

| النمط | المعنى | القاعدة |
|---|---|---|
| `current_snapshot` | صورة المحفظة عند لحظة التوليد | لا فلتر زمني عام. يمكن فلترة أعمدة تاريخية ظاهرة فقط إذا نص العقد عليها |
| `period_activity` | أحداث وقعت داخل فترة | `from/to` يطبقان على عمود حدث معرّف، وليس `updated_at` العام |
| `event_history` | إعادة بناء حالة كيان عند وقت سابق | يتطلب ledger/events مكتملة تغطي الإنشاء وكل الانتقالات؛ وإلا يُرفض العمود |

تواريخ Date-only تُعرض كـ `YYYY-MM-DD` دون إزاحة timezone. الأحداث Timestamp تُخزن وتنقل بصيغة معيارية وتُعرض بالمنطقة الزمنية المعتمدة.

### 9.5 البنية التقنية المشتركة

```text
Report Catalog / Definition
          │
          ├── Access Policy: identity + permission + scope + subject
          ├── Request Validator / Normalizer
          ├── Domain Query Service
          │       ├── scoped base subject
          │       ├── filter predicates
          │       ├── one-row-per-grain projection
          │       └── total count + stable ordering
          ├── Report Run / Immutable Snapshot
          ├── Excel Export of the same Snapshot
          └── Report UI + Guide + Freshness Metadata
```

#### 9.5.1 مسؤولية كل طبقة

| الطبقة | المسؤولية | ممنوع عليها |
|---|---|---|
| Catalog | وصف التقرير وأعمدته وفلاتره ونطاقاته | SQL وقرارات مستخدمين خاصة |
| Access Policy | حساب النطاق الفعلي وإثات subject | الاعتماد على الواجهة أو اسم الدور |
| Validator | تطبيع المدخلات ورفض القيم غير المعروفة | تحويل القيمة الخاطئة إلى “كل النتائج” |
| Query Service | قراءة مصادر الحقيقة ضمن النطاق | تخزين صلاحيات أو ترجمات UX متفرقة |
| Snapshot | حفظ العقد والفلاتر والصفوف وأثر التوليد | إعادة الاستعلام عند التصدير |
| Exporter | تحويل اللقطة نفسها إلى Excel | توسيع النطاق أو جلب بيانات أحدث |
| UI | إدارة الفلاتر، عرض الحداثة، التوليد، التصدير، والدليل | تقرير من يستطيع رؤية أي صف |

يجب أن يكون مسار العرض ومسار التصدير مستهلكين لنفس Report Definition ونفس Access Policy ونفس snapshot. يُمنع بناء SQL مستقل للتصدير.

### 9.6 عقد الوصول والنطاق

يطبق هذا القسم معيار هندسة الصلاحيات في [`permissions-engineering-standard.md`](permissions-engineering-standard.md):

```text
identity + permission + scope + subject = decision
```

- صلاحية العرض مستقلة عن صلاحية التصدير. التصدير لا يتجاوز تقاطع نطاق العرض ونطاق التصدير.
- `GLOBAL`: يرى كل الفروع، ويظهر له فلتر الفرع، ويضاف عمود **الفرع** لكل صف.
- `BRANCH`: يرى فرعًا من فروعه المعينة، ولا يختار فرعًا خارجها.
- `ASSIGNED`: لا يُسمح به إلا إذا حدد عقد التقرير subject وعلاقة إسناد حالية ومثبتة. لا يكفي وجود معرّف موظف بأحد الربطات.
- النطاق غير المدعوم يُرفض على الخادم، ويُخفى التقرير من الكتالوج؛ لا يُخفض بصمت إلى نطاق آخر.
- كل استعلام يبدأ من subject الرئيسي ويطبق شرط فرعه وإسناده قبل الربطات التفصيلية.
- يُسجّل مع اللقطة مفتاح الصلاحية والنطاق الفعلي والفرع المطلوب، لكن لا تُخزّن قرارات الوصول في المتصفح كمصدر حقيقة.

### 9.7 عقد الفلاتر

#### 9.7.1 قاعدة الوجود والقيمة

- لا يُضاف فلتر لحقل غير موجود في عقد التقرير. يجوز إخفاء العمود بصريًا فقط إذا بقي معرّفًا في العقد وشُرح سبب إخفائه.
- الفلتر يستخدم نفس دلالة العمود. لا يفلتر «تاريخ آخر زيارة» على `created_at` للمهمة.
- القيم تأتي من endpoint خيارات مقيّد بنفس Access Policy؛ لا تكشف قوائم الفروع أو الموظفين ما لا يمكن للمستخدم رؤيته في التقرير.
- القيمة غير المعروفة، والتاريخ المقلوب، والمدى العددي غير المنطقي تُرفض بـ `400` ذي رمز خطأ مستقر.
- يُطبّق الفلتر على الخادم ويُحفظ بصورته المطبّعة في اللقطة.

#### 9.7.2 الجغرافيا

الترتيب القانوني دومًا:

```text
المحافظة → المنطقة → الناحية → الحي
```

- اختيار مستوى أعلى يقيّد خيارات المستوى التالي.
- الاستعلام يعتمد معرّفات `geo_units` ويوسّع العقدة إلى ذريتها المسموحة.
- يجب تعريف علاقة موقع الصف: موقع الزبون، الجهاز، الزيارة، الفرع، أو غيره. لا يجوز الخلط بينها.
- عند عرض الجغرافيا في التقرير تظهر المستويات بهذا الترتيب، وتمثّل القيمة الفارغة كـ «غير محدد» لا كمستوى آخر مخمّن.

#### 9.7.3 الفرز

- الفرز جزء من مدخلات التوليد (`sortKey` و`sortDir`) ويُحفظ ضمن الفلاتر المطبّعة؛ لا يُطبّق على صفحة المتصفح الحالية وحدها.
- يعرّف الكتالوج الأعمدة القابلة للفرز. تقبل الأعمدة الرقمية والزمنية الفرز افتراضيًا، وتُفعّل الأعمدة النصية ذات الدلالة الواضحة صراحةً؛ لا تُفرز الروابط أو الملاحظات الطويلة وأرقام التواصل لمجرد أنها ظاهرة.
- يتحقق الخادم من مفتاح العمود واتجاه `asc|desc` مقابل Report Definition المرئي ضمن نطاق المستخدم. القيمة المجهولة تُرفض بـ `400` ولا تدخل SQL.
- ينفذ Query Service الفرز قبل بناء اللقطة، وينتهي دائمًا بالـ `defaultSort` الحتمي ككاسر تعادل. لذلك تتطابق الصفحات وExcel مع ترتيب اللقطة.
- تغيير الفرز بعد التوليد لا يعيد ترتيب عشرة صفوف محليًا؛ يضع الواجهة في حالة «تغيّر ترتيب التقرير — يلزم توليد جديد»، ويوقف التصدير والتنقل حتى إنشاء اللقطة الجديدة.

#### 9.7.4 فلاتر تقرير «ملف الأسماء»

- الفلاتر الأساسية: الفرع عند `GLOBAL`، الجغرافيا الهرمية، اسم الشخص المقترح، مصدر الاسم، حالته، مآله، حالة التكرار، ونطاق تاريخ إضافة الاسم.
- الفلاتر الإضافية: رقم لائحة الأسماء، نطاق تاريخ اللائحة، اسم الوسيط، تصنيفه، نطاق تاريخ زيارته، الفني المرافق، حالة وعد الهدية، والعمل.
- حالات الاسم والفنيون المرافقون وحالات وعود الهدايا تأتي من endpoint خيارات يطبق نطاق الفرع/الإسناد نفسه. القيم الثابتة مثل المصدر والمآل والتكرار تعرض مصطلحات عربية وترسل رموزًا داخلية ثابتة.
- «العمل» بحث نصي خادمي وليس قائمة خيارات؛ لأن عدد قيمه الحرة كبير، وتحميلها كاملة يضر الأداء وقابلية الاستخدام.
- لا توجد فلاتر للملاحظات أو العناوين أو أرقام التواصل. تغيير أي فلتر بعد التوليد يجعل اللقطة قديمة ويوقف التنقل والتصدير حتى إعادة التوليد.

#### 9.7.5 فلاتر تقرير «ملف البيعات اليومي»

- الفلاتر الأساسية: مدى تاريخ العقد (إلزامي)، الفرع عند `GLOBAL`، الجغرافيا الهرمية على موقع تركيب الجهاز، حالة العقد، مرحلة التنفيذ، البائع، قسم البائع، وطريقة الدفع.
- الفلاتر الإضافية: نوع البيعة، صفة البيعة، وجود متبقٍّ مالي، نوع الجهاز (الموديل)، وبيعة محددة.
- **لا فلتر نصي حرّ في هذا التقرير.** كل قيمة تُنتقى من قائمة مقيّدة أو حقل تاريخ، ولا يُدخل المستخدم نصًا في أي فلتر. السبب: المطابقة الجزئية تعيد صفوفًا غير مقصودة، والنص العربي الحرّ يختلف بالمسافات والهمزات فيُخفي مطابقات صحيحة، وقيمة غير معرَّفة كانت ستمر بلا رفض. البحث عن بيعة بعينها يتحقق بانتقاء صفها لا بكتابة اسمها.
- «بيعة محددة» منسدل يرسل **معرّف الصف** ويُطبَّق كمساواة على مفتاح الحبيبة، إضافةً إلى شرطي الفرع والإسناد لا بدلًا منهما؛ فبيعة خارج نطاق المستخدم تعود بصفر صفوف. وخياراته مقيّدة بمدى التاريخ المطلوب نفسه — أي بما يمكن أن يحويه التقرير فعلًا — وبحدّ أقصى معلَن في دليل التقرير لا صامت، وتغيير المدى يُسقط الاختيار السابق.
- نوع البيعة وصفتها قائمتان ثابتتان مصدرهما قيود `CHECK` في المخطط نفسها؛ والبائع وقسمه والموديل والبيعة تأتي من endpoint خيارات يطبق نطاق الفرع/الإسناد نفسه، فلا يكشف منسدل ما لا يظهر للمستخدم في التقرير.
- «وجود متبقٍّ مالي» يُطبَّق على مخرَج نفس التجميع الذي يغذّي عمود «المتبقي» الظاهر، لا على تعبير موازٍ. و«عليها متبقٍّ» تعني رصيدًا **أكبر من صفر** فقط؛ الرصيد السالب حالة إرجاع لا تحصيل فمكانه «مسدَّدة بالكامل»، ولا يُقدَّم وضع ثالث للسالب.
- **مال العقد لا مال الزبون:** دفتر الحركات على مستوى الزبون، وحركة مال المهمة تحمل معرّف عقد الجهاز أيضًا. فأي عمود أو فلتر مالي في تقرير حبيبته العقد يحصر الحركات بمصادر العقد نفسه (قيمته وأقساطه ودفعاته) عبر **قائمة سماح موجبة** لا استثناء لقائمة مهام — لأن مصدرًا ماليًا جديدًا كان سيتسرّب إلى رصيد العقد بصمت. ذمة الصيانة أو التركيب تبقى في كشف حساب الزبون وفي تقرير مال المهام، ولا تُقرأ كمتبقٍّ على البيعة.
- لا توجد فلاتر للملاحظات أو العناوين أو أرقام التواصل أو «مصدر البيعة» الحرّ. تغيير أي فلتر بعد التوليد يجعل اللقطة قديمة ويوقف التنقل والتصدير حتى إعادة التوليد.

### 9.8 التوليد، اللقطة، والتصدير

#### 9.8.1 سجل التوليد

يحفظ سجل التوليد على الأقل:

```text
runId
reportKey + definitionVersion
generatedAt + generatedByUserId
expiresAt + isPinned
effectiveScope + requestedBranchId + subjectSignature
normalizedFilters
columns
rowCount
rows or immutable result reference
query/schema version
```

- زر **توليد التقرير** هو العملية الوحيدة التي تنشئ run جديدًا.
- تغيير فلتر بعد التوليد يضع الواجهة في حالة «الفلاتر تغيّرت — يلزم توليد جديد»، ولا تغيّر اللقطة المعروضة.
- يظهر وقت التوليد والنطاق والفلاتر المطبّقة بوضوح فوق الجدول وفي الملف المصدّر.
- مدة الاحتفاظ الافتراضية باللقطة **30 يومًا من وقت إنشائها**، ويظهر `expiresAt` للمستخدم. يجوز تثبيت run تشغيليًا عبر `isPinned` لاستثنائه من التنظيف، من دون تغيير صلاحية الوصول إليه.
- ينفّذ التنظيف دوريًا وبصفوف محدودة، ولا يحذف إلا runs منتهية الصلاحية وغير مثبتة وحالتها `completed` أو `failed`. يستخدم الحجز `FOR UPDATE SKIP LOCKED` كي لا يتعارض أكثر من عامل تنظيف، وتُحذف صفوف اللقطة التابعة بالـ cascade.
- سجل تدقيق التصدير تاريخي ولا يُحذف بانتهاء اللقطة؛ عند حذف run تصبح إشارته إليه `NULL` مع بقاء هوية التقرير والمستخدم ووقت التصدير وقياساته محفوظة.

#### 9.8.2 عقد بناء اللقطة الكبيرة

- تمرّ جميع التقارير الجدولية عبر منفّذ اللقطة المشترك؛ يُمنع إنشاء مسار توليد خاص بتقرير يتجاوز هذا المنفّذ أو يغيّر دلالته.
- يُنفّذ استعلام التقرير مرة واحدة داخل معاملة `REPEATABLE READ`، ويُقرأ عبر PostgreSQL cursor على دفعات محدودة الذاكرة. الحجم الافتراضي للدفعة `1000` صف، ويُعدّل بالقياس لا بتغيير عقد التقرير.
- يجب أن يملك كل Report Query ترتيبًا حتميًا كليًا (`ORDER BY` ينتهي بمفتاح كاسر للتعادل) كي تبقى أرقام الصفوف ثابتة ولا تسقط أو تتكرر سجلات بين الدفعات.
- تُحفظ كل دفعة مباشرة في مخزن `report_run_rows` بترقيم متصل، ولا تُجمع كامل النتائج في ذاكرة API. لا يجوز وضع حد أعمال اعتباطي مثل 50 ألف صف أو إرجاع ملف مبتور بصمت.
- إنشاء `report_runs` وحفظ جميع صفوفه وتثبيت `rowCount` عملية ذرية واحدة: عند فشل أي دفعة تُلغى المعاملة كاملة ولا يبقى run جزئي قابل للعرض أو التصدير.
- يبدأ الطلب اليدوي بإنشاء run دائم بحالة `queued` ويعود فورًا؛ عامل خلفي ينتقل به إلى `running` ثم `completed` أو `failed`. يعيد العامل قرار الصلاحية قبل قراءة البيانات، ويعرض الخادم تقدم الصفوف والدفعات دون كشف صفوف جزئية.
- حجز الأعمال يستخدم `FOR UPDATE SKIP LOCKED` مع حد تزامن موزع على قاعدة البيانات، وتُستعاد الأعمال المتوقفة من heartbeat منتهٍ بعدد محاولات محدود.
- لا يجوز لاتصال التقدم الحي تحديث صف `report_runs` الذي ستعدّله معاملة اللقطة ذات `REPEATABLE READ`؛ تحفظ قيم `heartbeat` والتقدم أثناء التشغيل في `report_run_runtime` مستقل، ثم تُثبت النتيجة النهائية على `report_runs` داخل معاملة اللقطة. يمنع ذلك تعارض `could not serialize access due to concurrent update` مع بقاء التقدم مرئيًا.
- صفحات الواجهة تقرأ من اللقطة المحفوظة فقط عبر `page` و`limit`، والحد الافتراضي `10` صفوف. تغيير الصفحة لا يعيد الاستعلام من مصادر الحقيقة ولا ينشئ run جديدًا.
- التصدير يقرأ كامل الصفوف من اللقطة نفسها وبترتيبها المخزن؛ لا يعيد حساب التقرير ولا يعتمد صفحة الواجهة الحالية.
- تُقرأ صفوف Excel عبر cursor بدفعات ويُكتب workbook بأسلوب streaming إلى ملف مؤقت يُحذف بعد التنزيل؛ لا تُحمّل اللقطة أو الملف كاملين في ذاكرة API، وتُقسّم النتائج تلقائيًا عند حد صفوف Excel.
- الاختبارات الإلزامية لهذا العقد تشمل: صلاحية cursor لكل Report Query مسجل، عبور أكثر من دفعة مع اتصال أرقام الصفوف، rollback كامل عند الفشل، وثبات الصفحة والعدد الإجمالي والتصدير على run واحد.

#### 9.8.3 عقد Excel

- يُصدّر **كامل صفوف اللقطة**، لا صفحة الواجهة فقط.
- يحتوي الملف على عنوان التقرير، `runId`، وقت التوليد، وقت التصدير، والفلاتر، والنطاق.
- تُحفظ الأنواع: الأرقام أرقام، والمبالغ decimal بتنسيق مالي، والتواريخ تواريخ، وأرقام التواصل نصوص.
- النصوص الطويلة تُلف داخل الخلية، والرؤوس مثبتة، والفلاتر مفعلة، والاتجاه RTL مع محاذاة تناسب نوع القيمة.
- يُمنع Formula Injection: أي نص يبدأ بـ `=` أو `+` أو `-` أو `@` يُعالج كنص لا كصيغة.
- التصدير يعيد التحقق من صلاحية العرض والتصدير وملكية `runId` قبل تسليم الملف.

### 9.9 صحة SQL والأداء

- تُستخدم parameterized queries لكل قيمة. لا تُدمج قيم المستخدم داخل SQL.
- تُفصل مرحلة تحديد subject عن تجميع التفاصيل. يُختصر كل مصدر one-to-many قبل ربطه.
- عندما يمكن أن يأتي الربط من أكثر من مصدر مستقل، تُفصل المسارات القابلة للفهرسة بـ `UNION ALL` ثم تُجمع النتيجة، بدل شرط `OR` مترابط يمنع PostgreSQL من استثمار الفهارس بكفاءة.
- تستثمر الاستعلامات قيود التفرد المثبتة في المخطط؛ لا يُضاف `MAX` أو تجميع احترازي فوق علاقة one-to-one مثبتة لمجرد إخفاء احتمال تكرار غير موجود.
- المبالغ «المدفوعة» تُقرأ من حركات مالية فعلية، لا من مبلغ متوقع أو حقل نموذج.
- القيم المجمعة مثل القطع تحفظ الهوية والكمية، مثل «الاسم × العدد»، ولا تعتمد على معرّف قطعة إذا كان المصدر يحفظ snapshot اسم حرًّا.
- تُعالج `NULL` دلاليًا: «غير محدد» ليس صفرًا، و«لا توجد زيارة» ليس تاريخًا افتراضيًا.
- الترقيم يعتمد فرزًا مستقرًا. يُحسب العدد الكلي من نفس الاستعلام المقيّد أو من استعلام مكافئ مثبت.
- عند بناء لقطة كاملة لا يُعاد حساب `COUNT(*) OVER()` داخل كل صف؛ يكون `rowCount` هو عدد الصفوف المحفوظة فعليًا. يجوز إبقاء العدّ في مسارات القراءة المباشرة المنفصلة إذا احتاج عقدها ذلك.
- قراءة صفحات اللقطة تستخدم نطاق `row_number` على المفتاح `(run_id, row_number)`، لا `OFFSET` المتزايد الذي يمسح الصفوف السابقة كلما ابتعدت الصفحة.
- تُحفظ مع كل run قياسات مراحل التوليد: زمن تعريف cursor، جلب المصدر، كتابة اللقطة، عدد الدفعات، زمن الصفحة الأولى، والزمن الكلي. ويحفظ تدقيق التصدير زمن قراءة اللقطة وبناء الملف والحجم النهائي.
- تُفحص خطة الاستعلام على بيانات ممثلة. القبول الأولي: لا full scan غير مبرر لجداول كبيرة، ولا N+1، ولا تضخم صفوف قبل التجميع.
- الفهارس تُقترح من خطة الاستعلام وقياس البيانات، لا بالتخمين.

### 9.10 عقد API والواجهة

#### 9.10.1 API

يجب أن تدعم البنية على الأقل:

- قراءة الكتالوج المرئي حسب الصلاحيات.
- قراءة خيارات الفلاتر المقيّدة.
- توليد run يدوياً بطلب `POST` وبمدخلات مطبّعة.
- قراءة run وصفحاته دون إعادة الحساب.
- تصدير run محدد بعد إعادة قرار الوصول.

الاستجابة تحمل `runId`, `generatedAt`, `generatedBy`, `effectiveScope`, `filters`, `columns`, `rows`, `totalRows`, وحالة `canExport`. لا ترسل الواجهة مفاتيح صلاحيات كقرار، بل تستلم القرار المحسوب من الخادم.

#### 9.10.2 UX والكتابة

- تستخدم رؤوس الأعمدة مصطلحات واجهة المشروع: «مهمة عرض جهاز» و«مهمة مغلقة»، لا `device_demo` و`CLOSED`.
- تعرض الواجهة الفلاتر بترتيب القراءة: النطاق والفرع، الجغرافيا، الفلاتر الأساسية، ثم المتقدمة.
- يظهر زر توليد مستقل، ويبقى التصدير معطلًا قبل وجود run مولّد وقابل للتصدير.
- تظهر حالات: لم يُولّد، جارٍ التوليد، مولّد، الفلاتر تغيّرت، لا توجد نتائج، فشل قابل للمحاولة.
- يوجد Hint مجاور للعنوان/النطاق يفتح دليلًا يشرح الحبيبة، الأعمدة، الحسابات، الحالات، ومعنى «آخر».
- يثبت تراصف فلاتر RTL ومحاذات الجدول وعدم وجود horizontal overflow غير مقصود بفحص بصري على أحجام شاشات ممثلة.

### 9.11 مصفوفة الاختبار الإلزامية

#### 9.11.1 اختبارات العقد والاستعلام

| الفئة | الحالات الإلزامية |
|---|---|
| Grain | عدم تكرار مفتاح الحبيبة مع وجود 0/1/عدة سجلات في كل علاقة فرعية |
| Latest | حدثان متعادلان زمنيًا، حدث غير مؤهل أحدث، غياب الحدث، وارتباط الحدث بكيان آخر |
| Aggregates | تعدد القطع/الدفعات/المهام وإثات عدم التضاعف وعدم التلوث من subject آخر |
| NULL | السجل بلا فرع/جغرافيا/تواصل/حدث حسب قاعدة المجال |
| Filters | كل فلتر مستقل، تقاطع الفلاتر، القيمة الخاطئة، حدود التاريخ والمبلغ، وتطابق عدد الصفوف |
| Snapshot | تغير بيانات المصدر بعد التوليد لا يغيّر run القديم، والتصدير يطابقه |

#### 9.11.2 اختبارات الأمان

الحد الأدنى الإلزامي:

1. رفض غياب صلاحية العرض.
2. إخفاء التقرير من الكتالوج عند غيابها.
3. رفض فرع خارج الفروع المعينة.
4. رفض subject غير مسند في `ASSIGNED`.
5. رفض نطاق ممنوع للتقرير.
6. رفض التصدير بدون صلاحية التصدير حتى لو العرض مسموح.
7. رفض تصدير run من نطاق/مستخدم غير مخول.
8. اختبار المسار الصريح للـ super-admin.
9. اختبار كل نطاق مدعوم إيجابيًا وكل نطاق غير مدعوم سلبيًا.

#### 9.11.3 اختبارات التكامل والقبول

- API: validation، pagination، stable sort، total count، normalized filters، وأكواد الأخطاء.
- DB: تنفيذ SQL الفعلي على schema المستهدف بلا `42P01`/column drift، ومقارنة عينات باستعلامات مرجعية صغيرة.
- Migration: dry-run داخل transaction مع rollback يثت التوافق، ولا يُعد نشرًا.
- UI: التوليد اليدوي، الفلاتر المشروطة بالنطاق، الحالات الفارغة، Hint، RTL، الشاشة الصغيرة، وتغيير الفلاتر بعد التوليد.
- Excel: ملف قابل للفتح، مطابق للـ run، كامل الصفوف، الأنواع صحيحة، العربية سليمة، ولا formula injection.
- Performance: زمن تنفيذ وحجم ذاكرة مقاسان على بيانات ممثلة، مع حد واضح للصفوف ومنع التصدير الصامت المبتور.

| المحور | سؤال القبول | الدليل |
|---|---|---|
| الدلالة | هل كل صف وعمود يعنيان ما يقوله العنوان؟ | عقد معتمد + عينات محسوبة يدويًا |
| الاكتمال | هل يسقط الاستعلام سجلات صحيحة أو يضيف غير المؤهلة؟ | مقارنة counts مع مصادر مرجعية |
| عدم التضاعف | هل الحبيبة محفوظة بعد الربط؟ | `COUNT` مقابل `COUNT DISTINCT` |
| الزمن | هل «الحالي»/«خلال الفترة»/«كما كان» مميزة بوضوح؟ | اختبارات الحدود والأحداث |
| الأمان | هل كل صف داخل قرار `identity + permission + scope + subject`؟ | الاختبارات السلبية والإيجابية |
| الفلاتر | هل كل فلتر يطابق حقلًا معرّفًا ويعمل على الخادم؟ | اختبار مستقل لكل فلتر |
| اللقطة | هل العرض والتصدير يخصان لحظة التوليد نفسها؟ | اختبار immutability ومطابقة Excel |
| UX/Writing | هل يفهم مستخدم المشروع العناوين والحالات دون قراءة الكود؟ | مراجعة مصطلحات + فحص بصري |
| الأداء | هل ينتهي التوليد والتصدير ضمن الحد المعتمد دون بتر؟ | `EXPLAIN (ANALYZE, BUFFERS)` + قياس API/export |

### 9.13 قالب العمل المختصر لأي تقرير جديد

### 9.14 تعريف الانتهاء (Definition of Done)

لا يُعد التقرير مكتملًا حتى:

- يوجد عقد Report Definition كامل ومطابق للكود.
- تكون مصادر الحقيقة وحبيبة الصف ونمط الزمن مثبتة.
- يُفرض الوصول على الخادم في العرض والتصدير وخيارات الفلاتر.
- يكون التوليد يدويًا ووقته ظاهرًا، واللقطة ثابتة.
- يطابق Excel اللقطة ويحمل وقتي التوليد والتصدير.
- تكون الفلاتر من عقد التقرير ومختبرة فرديًا ومجتمعة.
- تنجح مصفوفة الأمان والعقد والتكامل وExcel وUX والأداء.
- تُقارن عينات من قاعدة بيانات ممثلة مع الحساب المرجعي المتوقع.
- يوثّق أي فرع منطقي لم تتوفر له بيانات حية، ويُثبت باختبار آلي واضح بدلًا من ادعاء تحققه تشغيليًا.
