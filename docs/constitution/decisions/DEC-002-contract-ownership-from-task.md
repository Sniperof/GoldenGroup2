> **التاريخ:** 2026-05-27

> **المعتمد:** إبراهيم عبيد
> **الفئة:** عقود مبيعات (Contracts) + مهام ميدانية (Open Tasks)
> **الإصدار:** 3.0 (مصحح — فصل سياق الزيارة عن مصدر المهمة وعن العرض الاختياري، مع حماية بيانات الترحيل)

## 1. الملخص التنفيذي (Executive Summary)

تحديد قاعدة منشأ وملكية البيعة للعقود الناتجة عن عمل ميداني: **سياق الزيارة، ومصدر المهمة، ومصدر العرض ثلاث علاقات مستقلة ولا يجوز دمجها في شرط واحد.**

- بعد تسجيل نتيجة مهمة عرض جهاز تتضمن عرضاً مقبولاً واحداً على الأقل، يظهر فعل إنشاء العقد في تفاصيل الزيارة. عند البدء منه تُثبَّت الزيارة والزبون والمهمة المسببة آلياً؛ ولا يختار المستخدم زبوناً آخر.
- اختيار عرض مقبول من مهمة `device_demo` **اختياري ومفضّل**، وليس شرطاً لإنشاء العقد.
- إذا اختير عرض، يصبح الربط به إلزامياً لذلك العقد وتُطبّق عليه قواعد التطابق والتفرّد.
- العقود اليدوية أو المهاجرة قد لا تحمل زيارة أو مهمة أو عرضاً، ولا يجوز اختلاق روابط تاريخية لها.

أي موظف بصلاحية إنشاء عقد (بما فيه المدير) — إذا دوره مش مشرف/فني — ملكيته للفرع فقط، وهو مجرد منشئ للعقد.

> ⚠️ **تصحيح مهم:** الفرق (`teams`) تُخزّن كـ JSONB داخل `day_schedules` وتتغير يومياً. لا يوجد `teams` table كيان ثابت. لذلك لا يمكن ربط العقد بـ "فريق" — الملكية فردية فقط.

## 2. السيناريو العملي (Practical Scenario)

```
مشرفة "سارة" من فرع حمص:
  │
  ├─ مهمة device_demo (task_id=501) ← assigned_employee_id = سارة
  │
  └─ الزبون وافق → المدير "خالد" ضغط "إنشاء عقد"
       │
       └─ العقد C-5002:
            ├─ source_open_task_id = 501 ← ربط كامل بالمهمة
            ├─ created_by = خالد ← للتدقيق فقط
            ├─ branch_id = فرع حمص ← الإيراد للفرع
            ├─ الملكية الفردية = سارة ← من assigned_employee_id
            └─ contract_referrer_id = الوسيط المختار (اختياري)
```

**النتيجة:** خالد (مدير) أنشأ العقد بس ملكيته للفرع. سارة (مشرفة) هي يلي "باعت" — بياخد الملكية الفردية.

## 3. القواعد الثابتة (Immutable Rules)

| # | القاعدة | التوضيح |
|---|---------|---------|
| **R-1** | **سياق الزيارة مستقل** | يظهر مسار العقد بعد نتيجة `device_demo` ذات عرض مقبول؛ وعند البدء منه تُستمد `source_visit_id` والزبون وفرع العملية من الزيارة ولا تُترك لاختيار المستخدم |
| **R-2** | **مصدر المهمة مستقل** | في مسار الزيارة يُربط العقد بـ`source_open_task_id` لمهمة `device_demo` التابعة لها؛ العقود اليدوية/المهاجرة قد تبقى بلا مهمة |
| **R-3** | **مصدر العرض اختياري** | بعد تحقق أهلية مسار الزيارة، يجوز إنشاء العقد دون `source_task_offer_id`؛ اختيار العرض ليس شرطاً لحفظ العقد |
| **R-4** | **الربط المختار صارم** | إذا اختير عرض، يجب أن يكون `accepted`، تابعاً للمهمة والزبون والفرع نفسيهما، وغير مرتبط بعقد حي آخر |
| **R-5** | **عقد حي واحد لكل عرض** | لكل عرض مقبول عقد واحد كحد أقصى ما دام العقد غير ملغى/مستبعد؛ إلغاء العقد يحرر العرض وفق سياسة دورة الحياة |
| **R-6** | **الملكية الفردية من المهمة عند وجودها** | تُشتق من الموظف المسؤول عن مهمة العرض وفق نموذج `sale_owner_id`؛ غياب المهمة لا يبرر تخمين مالك للبيعة |
| **R-7** | **created_by للتدقيق فقط** | من ضغط "إنشاء عقد" لا يحدد ملكية البيعة |
| **R-8** | **الإيراد دائماً للفرع** | `contracts.branch_id` هو مصدر الإيراد مهما كان صاحب الملكية |
| **R-9** | **البيانات التاريخية لا تُخترع** | NULL في روابط الزيارة/المهمة/العرض مسموح للعقود المهاجرة أو المدخلة مباشرة؛ لا backfill تخميني ولا تطبيق رجعي لحراس الإنشاء الجديدة |

## 6. العلاقات التحديثية (Updated Relationships)

```
open_tasks (المهمة)
  │
  ├─ assigned_employee_id → المشرفة/الفني
  │
  └─ ينتج → contracts (source_open_task_id)
       │
       ├─ branch_id → الفرع (الإيراد)
       ├─ created_by → المنشئ (للتدقيق فقط)
       ├─ contract_referrer_id → الوسيط (اختياري)
       │
       └─ الملكية الفردية ← من assigned_employee_id (عبر المهمة)
```

أما مسار الإنشاء من الزيارة فهو:

```text
field_visit (سياق العملية والصلاحية)
  ├─ client_id       → زبون مثبت
  ├─ branch_id       → فرع مثبت
  └─ device_demo open_task → مصدر المهمة
       └─ accepted offer   → مصدر عرض اختياري
```

وجود زيارة أو مهمة لا يفرض اختيار عرض. لكن عند اختيار عرض لا يجوز فك العلاقة أو تبديل الزبون/المهمة/الفرع أثناء الحفظ.
