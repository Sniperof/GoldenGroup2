# مكون مشترك: لقطة بيانات المرشح (CandidateSnapshot)

> **النوع:** Shared UI Component  
> **الحالة:** V1 معتمد، وقسم وعود الهدايا V2 معتمد — 2026-07-29
> **الهدف:** توحيد عرض بيانات المرشح على 3 مستويات بكل مشروع Golden CRM  
> **القاعدة:** المرشح هو نفسه — الشكل بس هو يلي بيتغيّر حسب السياق  
> **الفرق عن ClientSnapshot:** المرشح ما عندو `gender` (ما في avatar بلون) — بدالو `status` badge + معلومات الإحالة

---

## المستوى الأول: Mini Snapshot (للقوائم والجداول)

### التعريف

لقطة مصغّرة بتظهر بقوائم المرشحين. الهدف: موظف التسويق أو المشرف يعرف **مين المرشح**، **حالتو**، **من وين جاء**، وبينقر عليه للتفاصيل.

**القاعدة الأساسية:**
- العنوان = `address_text` مباشرة (أو `geo_unit.name` إذا `address_text` فاضي)
- الحالة (`status`) **دايماً** تظهر — هاد أهم معلومة عن المرشح
- Western numerals فقط

---

### الحقول (DB → UI)

| الحقل بالعربي | اسم الحقل بالكود | مصدره بالـ DB | نوع الـ DB | NULL? | كيف بنعرض؟ |
|---|---|---|---|---|---|
| الاسم الكامل | `fullName` | `candidates.first_name` + `candidates.last_name` | `VARCHAR` | ✅ | سطر واحد bold |
| الحالة | `status` | `candidates.status` | `VARCHAR(50)` | ✅ | **badge — أولوية قصوى** |
| العنوان المختصر | `addressShort` | `candidates.address_text` أو `geo_units.name` | `TEXT` / `VARCHAR` | ✅ | سطر واحد |
| المصدر | `referralSource` | `candidates.referral_type` + `referral_name_snapshot` | `VARCHAR` | ✅ | "من: اسم المحيل" |
| المسؤول | `ownershipDisplay` | `candidate_assignments` JOIN `hr_users` أو `candidates.branch_id` | — | ✅ | اسم الموظف المسؤول الواحد، أو اسم الفرع فقط عند ملكية الفرع |

---

### الحالة (`status`) — Badge Colors

| الحالة | اللون | المعنى |
|--------|-------|--------|
| `Suggested` | 🔵 أزرق فاتح | مقترح/ميداني — جديد |
| `New` | ⚪ رمادي | يدوي — جديد |
| `Contacted` | 🟡 أصفر | تم الاتصال |
| `FollowUp` | 🟠 برتقالي | بمتابعة |
| `Qualified` | 🟢 أخضر | مؤهل للشراء |
| `Junk` | 🔴 أحمر | مرفوض/غير جدي |

**القاعدة:** الـ badge **دايماً** ظاهر — حتى لو الاسم فاضي.

**قرار معتمد 2026-07-29 — استقلال الحالة عن التحويل والتكرار:**
- شارة الحالة مشتقة حصراً من `candidates.status` ولا يتغير نصها بسبب `duplicate_flag` أو `converted_to_lead_id`.
- `Qualified` تُعرض **"مؤهل"** دائماً. إذا كانت `converted_to_lead_id` موجودة، تظهر شارة تحويل مستقلة بجانبها.
- `duplicate_flag` يظهر كتنبيه مستقل ولا يحوّل تسمية الحالة إلى "تم الربط" أو "تم التحويل".

### المصدر (`referralSource`)

| `referral_type` | العرض |
|-----------------|-------|
| `Client` | "عميل: [referral_name_snapshot]" |
| `Employee` | "موظف: [referral_name_snapshot]" |
| `Personal` | "شخصي: [referral_name_snapshot]" |
| `null` | ما بنعرض السطر |

### 🎨 مثال واضح (Visual Example)

**البيانات من الـ DB:**
```json
{
  "first_name": "سمير",
  "last_name": "الحموي",
  "address_text": "حمص، الإنشاءات، شارع البرازيل",
  "status": "Suggested",
  "referral_type": "Client",
  "referral_name_snapshot": "محمود البكري"
}
```

**كيف بيظهر بالـ UI (Mini Snapshot):**
```
┌─────────────────────────────────────────────┐
│  سمير الحموي  [مقترح]                       │  ← bold + status badge
│  حمص، الإنشاءات، شارع البرازيل               │  ← grey
│  عميل: محمود البكري                         │  ← grey (referral source)
│  علي المحمد +1                              │  ← grey (ownership)
└─────────────────────────────────────────────┘
```

**إذا `status = "Qualified"`:**
```
┌─────────────────────────────────────────────┐
│  باسل عمر  [مؤهل]                           │  ← bold + أخضر badge
│  دمشق، المزة                                  │
│  موظف: سامي فهد                              │
│  أحمد علي                                   │
└─────────────────────────────────────────────┘
```

**إذا `status = "Junk"`:**
```
┌─────────────────────────────────────────────┐
│  خالد فهد  [مرفوض]                          │  ← bold + أحمر badge ( strikethrough )
│  العنوان: —                                   │
└─────────────────────────────────────────────┘
```
> **ملاحظة:** الاسم المرفوض (`Junk`) ممكن يظهر grey-out أو strikethrough حسب السياق.

## المستوى الثاني: Standard Snapshot (لصفحة المرشح وتفاصيل الإحالة)

> **هاد "لب المرشح" — أهم مستوى. بيظهر بصفحة تفاصيل المرشح، صفحة الإحالة، وتفاصيل المهمة المرتبطة.**

### التعريف

لقطة قياسية تعرض بيانات الاسم المقترح اللازمة للمراجعة والقرار. تبقى أرقام الهاتف للقراءة فقط ومن دون إجراءات أو سجل تواصل، وتضيف V2 قسم وعود الهدايا للقراءة فقط.

**الفرق عن المستوى الأول:**
- الاسم بيتفكّك (first + last + nickname)
- العنوان كامل (`address_text` أو geo hierarchy)
- معلومات الإحالة بالتفصيل (من وين جاء، ليش، امتى)
- المهنة
- ملاحظات
- تنبيه التكرار (Duplicate Warning)
- المسؤول/ين
- رابط التحويل لزبون (إذا `converted_to_lead_id` موجود)

---

### الحقول (DB → UI)

#### أ) الهوية الكاملة

| الحقل بالعربي | اسم الحقل بالكود | مصدره بالـ DB | نوع الـ DB | NULL? | قاعدة العرض |
|---|---|---|---|---|---|
| الاسم الأول | `firstName` | `candidates.first_name` | `VARCHAR(255)` | ✅ | سطر أول bold |
| الكنية | `lastName` | `candidates.last_name` | `VARCHAR(255)` | ✅ | يلحق firstName |
| اللقب | `nickname` | `candidates.nickname` | `VARCHAR(255)` | ✅ | بين قوسين بعد الاسم |
| الحالة | `status` | `candidates.status` | `VARCHAR(50)` | ✅ | **badge جانب الاسم** — ألوان حسب الجدول فوق |

**قرار معتمد 2026-07-29 — رأس تفاصيل الاسم المقترح:**
1. الترتيب البصري الملزم: **الاسم ← الحالة ← الفرع والمسؤول ← رقم السجل وتاريخ الإضافة**.
2. الاسم الأساسي هو `firstName + lastName`، ويظهر `nickname` بين قوسين بعده.
3. إذا غاب `firstName`، يكون fallback بالترتيب: `nickname` ثم `lastName`.
4. إذا غابت جميع أجزاء الاسم، يظهر النص **"اسم غير مكتمل"**؛ ولا يستخدم رقم الهاتف بديلاً عن الاسم.
5. رقم السجل وتاريخ الإضافة معلومات ثانوية، ولا ينافسان الاسم أو الحالة بصرياً.
6. لا يُعرض `ownerUserId` الإرثي. المسؤولية مشتقة من `ownershipType` و`responsibleUserId` و`ownershipLabel`.

**مثال بالـ UI:**
```
سمير الحموي (أبو أحمد)                         [قيد المتابعة]
الاسم المقترح #102
فرع حمص  •  المسؤول: علي المحمد  •  أضيف في 2026-05-10
```

---

#### ب) أرقام الهاتف — عرض فقط في V1

**قرار معتمد 2026-07-29:**
1. يعيد DTO تفاصيل الاسم قائمة `phoneNumbers` مشتقة من `mobile` و`contacts`، وتعرض الصفحة الأرقام للقراءة فقط.
2. يحافظ كل عنصر على المعلومات المخزنة: `type` لنوع الرقم، و`label` لمن يعود الرقم، و`hasWhatsApp` لدعم واتساب، و`isPrimary`، و`status`. القيمة غير الموجودة تاريخياً تعرض «غير محدد» ولا تُخمن.
3. هذه الخصائص وصفية فقط؛ لا تظهر أزرار اتصال أو واتساب أو نسخ.
4. لا يعرض سجل محاولات أو نتائج التواصل أو مواعيد المتابعة.
5. إضافة إجراءات التواصل إلى الصفحة مرحلة مستقلة لاحقة تحتاج قرار منتج وعقد صلاحيات وتدقيق جديداً؛ ولا تعتبر جزءاً ضمنياً من V1.

---

#### ج) العنوان (Address)

| الحقل بالعربي | اسم الحقل بالكود | مصدره بالـ DB | نوع الـ DB | NULL? | قاعدة العرض |
|---|---|---|---|---|---|
| الموقع الجغرافي | `geoUnitId` + `geoPath` | `candidates.geo_unit_id` + سلسلة آباء `geo_units` | — | ✅ | المسار الإداري الكامل من المحافظة إلى أعمق مستوى |
| العنوان التفصيلي | `addressText` | `candidates.address_text` | `TEXT` | ✅ | وصف مستقل للشارع والبناية والطابق والعلامة المميزة |

**قرار معتمد 2026-07-29 — الموقع الجغرافي والعنوان التفصيلي:**
1. `geoUnitId` هو مصدر الموقع الإداري المنظم المستخدم للنطاق والتوزيع والتصفية، و`addressText` وصف مكاني حر مستقل؛ لا يحل أحدهما محل الآخر.
2. صفحة التفاصيل تعرض كامل `geoPath` من المحافظة إلى أعمق مستوى، ثم تعرض `addressText` في سطر مستقل. القائمة تعرض آخر مستويين من المسار، ثم تستخدم `addressText` كـfallback، ثم "—".
3. يجوز للاسم المقترح أن يحفظ أي مستوى من 1 إلى 4 لأن معلوماته قد تكون أولية، مع إظهار مستوى الدقة: محافظة، منطقة/مدينة، ناحية/حي كبير، أو حي دقيق/قرية.
4. إذا وجد `geoUnitId` بلا `addressText` يظهر المسار مع "العنوان التفصيلي: غير مدخل"، ولا ينسخ اسم الوحدة تلقائياً إلى `addressText`.
5. إذا وجد `addressText` بلا `geoUnitId` يعرض النص مع تنبيه **"الموقع الجغرافي غير محدد"**.
6. إذا وجد الحقلان يعرضان منفصلين. وإذا طابق النص تماماً اسم آخر وحدة — نتيجة السلوك التاريخي القديم — لا يكرر كسطر تفصيلي ويصنف السجل للمصالحة عند التعديل.
7. لا يفسر النظام النص الحر ولا يصحح تعارضه مع المسار تلقائياً؛ يعرض القيمتين كما حفظتا ويترك التصحيح لمستخدم مخول.
8. الوحدة `inactive` تبقى ظاهرة تاريخياً مع شارة **"وحدة جغرافية معطلة"**، ولا تكون قابلة للاختيار لسجل جديد أو عند تغيير الموقع.
9. عند الإنشاء أو تغيير الموقع يعيد الخادم التحقق من وجود الوحدة وفعاليتها ووقوعها ضمن تغطية فرع الاسم. تعديل حقل آخر لا يفشل بسبب وحدة تاريخية معطلة ما دام الموقع لم يتغير.
10. استجابة التفاصيل تعيد `geoPath` بعد تفويض الاسم، ولا تعتمد فقط على lookup الواجهة، حتى يبقى المسار التاريخي قابلاً للعرض.

---

#### د) معلومات الإحالة (Referral Info)

> هاد الفرق الأكبر عن ClientSnapshot — المرشح عندو "من وين جاء"

| الحقل بالعربي | اسم الحقل بالكود | مصدره بالـ DB | نوع الـ DB | NULL? | قاعدة العرض |
|---|---|---|---|---|---|
| نوع الإحالة | `referralType` | `candidates.referral_type` | `VARCHAR(100)` | ✅ | "عميل" / "موظف" / "شخصي" |
| اسم المحيل | `referralName` | `candidates.referral_name_snapshot` | `VARCHAR(255)` | ✅ | "من: [الاسم]" |
| معرف المحيل | `referralEntityId` | `candidates.referral_entity_id` | `INTEGER` | ✅ | `clients.id` للزبون أو `employees.id` للموظف |
| قناة الإحالة | `referralOriginChannel` | `candidates.referral_origin_channel` | `VARCHAR(100)` | ✅ | badge صغير — PhoneCall / Campaign / WhatsApp |
| سبب الإحالة | `referralReason` | `candidates.referral_reason` | `TEXT` | ✅ | expandable text |
| تاريخ الإحالة | `referralDate` | `candidates.referral_date` | `VARCHAR(50)` | ✅ | تاريخ |
| رقم ورقة الإحالة | `referralSheetId` | `candidates.referral_sheet_id` | `INTEGER` | ✅ | رابط لـ `referral_sheets` |

**قرار معتمد 2026-07-29 — طريقة الإدخال والوسيط:**
1. طريقة الإدخال مستقلة عن نوع الوسيط: `referralSheetId` موجود يعني "من لائحة أسماء"، وغيابه يعني "إدخال مباشر". لا يستخدم `referralReason` لتخزين `Direct Referral` أو `Part of Sheet`.
2. أنواع الوسيط:
   - `Client`: زبون، و`referralEntityId` يشير إلى `clients.id`.
   - `Employee`: موظف، و`referralEntityId` يشير إلى `employees.id` لا `hr_users.id`.
   - `Personal`: استقطاب شخصي باسم المستخدم وقت التسجيل، بلا رابط كيان مفترض.
   - `Unknown`: وسيط مجهول، بلا رابط.
3. `referralNameSnapshot` لقطة تاريخية ثابتة للاسم وقت الترشيح ولا تتغير مع الاسم الحي. إذا كان المرجع الحي متاحاً ومخولاً، يعرض اسمه الحالي ورابطه، ويعرض الاسمان معاً عند اختلافهما.
4. رؤية الاسم المقترح لا تمنح تلقائياً رؤية الزبون أو الموظف الوسيط. يعرض الاسم التاريخي كنص دائماً، ولا يظهر رابط أو رقم سجل الكيان إلا بعد تفويض الكيان المرتبط.
5. قنوات الوصول تعرض مستقلة: `Acquaintance` معرفة شخصية، `PhoneCall` مكالمة هاتفية، `SocialMedia` وسائل التواصل الاجتماعي، `Campaign` حملة إعلانية، و`App` التطبيق. لا تحول `App` إلى `SocialMedia`.
6. `referralDate` هو تاريخ حدوث الترشيح، و`createdAt` تاريخ إدخال السجل إلى النظام؛ يعرضان كمفهومين منفصلين.
7. `referralConfirmationStatus` حقل غير مستخدم حالياً، لذلك لا يدخل في عقد تفاصيل V1 ولا يظهر في الصفحة. يبقى في التخزين والعقود القديمة إلى حين قرار ترحيل مستقل.
8. سبب الترشيح يعرض بالعربية. تحول القيمتان التاريخيتان `Direct Referral` و`Part of Sheet` عند القراءة إلى **«ترشيح مباشر»** و**«ضمن لائحة أسماء»**، وتعرض أي قيمة وصفية أخرى كما خزنت.
9. عند الإنشاء من لائحة، يرث الاسم خادمياً من اللائحة: الفرع، المسؤول/ملكية الفرع، نوع الوسيط، معرفه، لقطة اسمه، قناة الوصول، تاريخ اللائحة، عنوان الوسيط عند استعماله، ورقم اللائحة. لا يقبل الخادم قيماً موازية لهذه الحقول من الواجهة.
10. في وضع «عبر لائحة أسماء» تعرض الواجهة اختيار اللائحة أولاً، ولا تعرض حقول فرع الاسم أو نوع ملكيته أو المسؤول عنه، ولا ترسل `ownershipType` أو `responsibleUserId` من المتصفح. يستمدها الخادم حصراً من اللائحة المختارة.
11. تحمل نافذة الإضافة اللوائح المخولة مباشرة عند فتح وضع اللائحة. لا تحول فشل التحميل إلى قائمة فارغة صامتة؛ تعرض حالة تحميل، ورسالة الخطأ مع إعادة المحاولة، أو رسالة عدم وجود لائحة `New`/`In-Progress` ضمن النطاق.
12. بعد الإنشاء تبقى حقول الاسم لقطة تاريخية. اختلافها عن اللائحة لاحقاً لا يصحح تلقائياً؛ تعرض بيانات الاسم مع تنبيه **"معلومات الترشيح لا تطابق لائحة المصدر"** للمخولين بالمراجعة، وتتم المصالحة تشغيلياً.

**قرار معتمد 2026-07-29 — بطاقة لائحة المصدر:**
1. إذا كان الاسم ناتجاً عن لائحة، تعرض بطاقة اللائحة فقط بعد نجاح تفويض `candidates.name_lists.view_list` على موضوع اللائحة نفسه. عند غياب التفويض يظهر فقط **"مصدر الإدخال: لائحة أسماء"** دون رقم أو موظفين أو إحصاءات.
2. البطاقة المخولة تعرض: رقم اللائحة، حالتها، تاريخها، فرعها، مصدرها اليدوي أو الزيارة، جامع الأسماء، مسؤول مراجعتها، قائد فريق الزيارة عند وجوده، عدد الأسماء الفعلي/المستهدف، مؤشري الجودة والتحويل، وملاحظات اللائحة.
3. حالات اللائحة تعرض كالتالي: `New` جديدة، `In-Progress` قيد الجمع، `Completed` مكتملة، و`Archived` مؤرشفة.
4. تفصل أدوار العاملين ولا تستخدم تسمية مدمجة:
   - `ownerUserName`: جامع الأسماء الفعلي.
   - `assignedHrUserName`: مسؤول مراجعة اللائحة.
   - `teamResponsibleUserName`: مسؤول فريق الزيارة.
   - `createdByUserName`: منشئ سجل اللائحة.
   ولا يخلط أي منها مع مسؤول الاسم الحالي.
5. العدد الفعلي يحسب خادمياً من سجلات `candidates` المرتبطة، ولا يعتمد وحده على `total_candidates` المخزن. يعرض المستهدف إذا كان أكبر من صفر.
6. الجودة والتحويل مؤشرا أداء للائحة كلها، ولا يعرضان كتقييم شخصي للاسم المفتوح. لا يعرض ترتيب الاسم داخل اللائحة لعدم وجود حقل ترتيب موثوق.
