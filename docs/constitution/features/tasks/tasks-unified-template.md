## 1. البنية العامة — القالب الموحد

### 1.1 هيكل صفحة التفاصيل (TaskDetailLayout)

```
┌─────────────────────────────────────────────────────┐
│  HEADER: اسم الزبون · نوع المهمة · حالتها · زر رجوع │
├─────────────────────────────────────────────────────┤
│  TAB BAR: [نظرة عامة][بيانات الزبون][العقد والجهاز] │
│           [التواصل والمتابعة][...تابات إضافية...][النتيجة] │
├─────────────────────────────────────────────────────┤
│                                                     │
│  محتوى التاب النشط                                  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### 1.2 التابات الأساسية — ثابتة لجميع المهام

| التاب | المحتوى الثابت | قابل للتخصيص |
|-------|---------------|--------------|
| **نظرة عامة** | ملخص المهمة (حالة، أولوية، سبب) + الجدولة + بيانات الإنشاء + إحصائيات سريعة | `overviewExtraCards` + `scheduleExtraRows` |
| **بيانات الزبون** | لقطة الزبون (اسم، هاتف، عنوان كامل، أرقام تواصل) | ❌ |
| **العقد والجهاز** | لقطة العقد (رقم العقد، الجهاز، عنوان التركيب، المالية) | ❌ |
| **التواصل والمتابعة** | اتصالات التيلماركتر + سجل الأحداث + نموذج إضافة ملاحظة | ❌ |
| **النتيجة** | ملخص النتيجة (outcome، حالة، تاريخ إتمام، ملاحظات) | `ResultRenderer` |

### 1.3 البيانات المحملة — ثابتة لجميع المهام

| الحقل | الوصف |
|-------|-------|
| `task` | بيانات المهمة + snapshots (clientSnapshot, contractSnapshot, teamSnapshot) |
| `activity[]` | سجل الأحداث (task_activity_log) |
| `calls[]` | اتصالات التيلماركتر |
| `devices[]` | أجهزة مرتبطة (open_task_devices) |
| `preOffers[]` | عروض مسبقة (open_task_pre_offers) — يستخدمها device_demo فقط |

### 1.4 الحالات — 11 حالة مشتركة لجميع المهام

```
open → needs_follow_up → assigned → in_scheduling → scheduled
→ waiting_execution → in_execution → ended
→ completed / closed / cancelled
```

## 2. نقاط التخصيص — ما يختلف بين أنواع المهام

كل نوع مهمة يحتاج لتعريف 4 عناصر فقط ضمن `TaskTypeExtension`:

```typescript
const xyzExtension: TaskTypeExtension = {
  // 1. بطاقات إضافية في نظرة عامة (اختياري)
  overviewExtraCards: (data) => <XyzOverviewCards data={data} />,

  // 2. تابات إضافية بين "التواصل" و"النتيجة" (اختياري)
  extraTabs: [
    { id: 'xyz_info', label: 'معلومات XYZ', render: (data) => <XyzInfoTab data={data} /> }
  ],

  // 3. عارض النتيجة الخاص بالنوع (اختياري)
  ResultRenderer: XyzResultRenderer,

  // 4. أزرار في شريط التابات بعد تسجيل النتيجة (اختياري)
  tabBarActions: (data) => <XyzActions data={data} />,
};
```

### 2.1 مقارنة الأنواع المنفذة

| العنصر | device_demo | emergency_maintenance | device_delivery |
|--------|-------------|----------------------|-----------------|
| **تاب إضافي** | "تفاصيل العرض" (preOffers) | "تفاصيل الطوارئ" | "معلومات التركيب" |
| **scheduleExtraRows** | موعد الزيارة + وقتها | — | تاريخ الزيارة + وقتها + نوع المهمة |
| **ResultRenderer** | جدول العروض + ردود الزبون | بطاقة قرار الطوارئ | نجاح/فشل التسليم |
| **tabBarActions** | — | وصل الصيانة | — |
| **overviewIssuesFor** | مشاكل حسب نوع المهمة | — | سيريال رقم مفقود |
| **hasResultFor** | `outcome != null` | `em_costs_id != null` | `result != null` |

## 3. إنشاء المهمة

### 3.1 البيانات الإلزامية

| الحقل | إلزامي | ملاحظات |
|-------|--------|---------|
| `client_id` | ✅ دائماً | لأي مهمة |
| `branch_id` | ✅ دائماً | يُؤخذ تلقائياً من المستخدم |
| `task_type` | ✅ دائماً | من قائمة الـ 20 نوع |
| `task_family` | ✅ دائماً | يُحدد من `task_type_config` |
| `reason` | ✅ دائماً | من `system_lists` |
| `contract_id` | حسب النوع | إذا `contract_required = TRUE` في `task_type_config` |
| `due_date` | حسب النوع | إذا `has_due_date = TRUE` في `task_type_config` |
| `priority` | اختياري | high / medium / low |
| `notes` | اختياري | — |
| `devices[]` | اختياري | أجهزة مرتبطة |
| `preOffers[]` | اختياري | عروض مسبقة |

### 3.1.1 قاعدة ربط الجهاز والعقد

القاعدة الأساسية في المهام التي تخص جهازاً مادياً:

`identity + permission + scope + installed_device subject = task eligibility`

- `installedDeviceId` / `open_tasks.device_id` هو رابط الجهاز التشغيلي الأساسي.
- `contractId` ليس شرطاً عاماً لإنشاء مهمة على جهاز. وجوده يعني أن المهمة لها سياق عقدي/مالي إضافي.
- الجهاز الخارجي يدخل النظام كصف في `installed_devices` مع `contract_id = NULL`، ويعامل كجهاز حقيقي في المهام التشغيلية.
- أي مسار يملك `device_id` صالحاً يجب أن يبني `deviceSnapshot` من `installed_devices` حتى لو كان `contractSnapshot = null`.
- لا يستخدم `contract_id` كبديل عن تحميل الجهاز والتحقق من `branch_id` و`customer_id` وحالة الجهاز.
- اشتراط العقد مسموح فقط عندما يكون موضوع المهمة هو العقد أو ذمة عقدية، لا عندما يكون موضوعها جهازاً مادياً.

### 3.2 مصادر الإنشاء

| المصدر | `source` في DB | من يضيف | الصفحة |
|--------|---------------|---------|--------|
| يدوي | `manual` | موظف صلاحية `marketing_visits.update_result` | POST /open-tasks |
| التيلماركتر | `telemarketing` | موظف تيلماركتر خلال جلسة | TelemarketerWorkspace |
| طلب طوارئ | `emergency_ticket` | أي موظف يقدم طلب | نموذج الطوارئ |
| النظام تلقائياً | `system` | بعد تسجيل نتيجة معينة | — |
| إنشاء عقد | `system` | بعد حفظ عقد جديد | ContractForm |

### 3.3 قاعدة المهمة الواحدة

يتحكم `task_type_config.allow_multiple`:

- `FALSE` (الأغلبية): مهمة واحدة نشطة فقط لكل زبون من نفس النوع في مرحلة "قيد الانتظار"
- `TRUE`: يمكن عدة مهام متوازية (طوارئ، دورية، تحصيل، هدايا، تشييك)

## 4.9 جرد أهلية المهام حسب الجهاز الخارجي والعقد

هذا الجرد يثبت التفريق بين **موضوع المهمة** و**السياق المالي**. وجود جهاز خارجي يعني وجود `installed_devices.id` بلا عقد بيع، وليس غياب subject تشغيلي.

| نوع المهمة | الموضوع الأساسي | هل يعمل على جهاز خارجي؟ | هل العقد مطلوب؟ | الحكم العملي |
|---|---|---:|---:|---|
| `device_demo` | زبون/عرض بيع | لا ينطبق | لا | ليست مهمة جهاز مثبت. |
| `device_purchase` | عقد بيع | لا | نعم | مسار بيع/عقد، وليس خدمة جهاز خارجي. |
| `device_delivery` | جهاز مادي | نادر/حسب الحالة | فقط عند `sale_delivery` | يعتمد على `device_id` وحالة التسليم؛ الجهاز الخارجي الذي أُدخل كقائم عند الزبون لا يحتاج تسليم عادة. |
| `device_installation` | جهاز مادي وموقع تركيب | نعم إذا كانت حالته تؤهل للتركيب | لا | يجب أن يكفي `device_id`، والعقد سياق اختياري. |
| `device_activation` | جهاز مركب | نعم إذا كانت حالته `installed` | لا | الدستور يسمح بالتشغيل لجهاز مركب سابقاً أو خارجي. |
| `device_checkup` | جهاز مادي | نعم | لا | فحص/تشييك تشغيلية مباشرة على الجهاز. |
| `device_disconnection` | جهاز مادي | نعم | لا | الفك يقرأ حالة الجهاز وموقعه، لا العقد. |
| `device_transfer` | جهاز مادي/حيازة/عنوان | نعم | لا | النقل يعمل على `device_id` وقد يغير الموقع أو الحيازة. |
| `device_retrieval` | جهاز مفكوك | نعم | لا | السحب يعتمد على حالة الجهاز وفك سابق، لا على العقد. |
| `device_return` | جهاز في الورشة | نعم | لا | الإرجاع يعتمد على سحب صيانة سابق وبيانات موقع الجهاز. |
| `emergency_maintenance` | عطل على جهاز | نعم | لا لطارئة لمرة واحدة | الجهاز الخارجي يكفيه `installed_device_id`; المالية يجب أن ترتبط بالمهمة/ذمة خدمة لا بعقد بيع. |
| `periodic_maintenance` | خدمة متكررة لجهاز | نعم بشرط | ليس عقد بيع؛ يحتاج عقداً أو `service_agreement` | جهاز خارجي بلا اتفاق خدمة لا يملك أساس جدولة دورية. |
| `installment_collection` | قسط/ذمة عقد | لا | نعم أو مصدر ذمة معتمد | لا تنشأ من جهاز خارجي بلا مصدر مالي مستقل. |
| `maintenance_collection` | ذمة صيانة | نعم إذا وجدت ذمة صيانة | لا كعقد بيع | تحتاج `receivable_source` واضحاً، لا يكفي وجود الجهاز وحده. |
| `parts_sale` | بيع قطع/مخزون | نعم مستقبلاً | لا كعقد بيع | يحتاج نموذج بيع قطع ومخزون مكتمل. |
| `device_repair` | إصلاح جهاز | نعم مستقبلاً | لا | عملياً يُغطى حالياً عبر الصيانة الطارئة/الدورية أو سحب/إرجاع. |
| `gift_delivery` | استحقاق هدية | لا عادة | حسب مصدر الاستحقاق | إذا كانت الهدية من عقد فهي عقدية، لا جهاز خارجي. |
| `golden_warranty` | كفالة/اتفاق | لا كمسار قديم | نعم/اتفاق كفالة | النوع القديم غير معتمد كمسار تشغيل كامل حالياً. |
| `golden_warranty_offer` | عرض كفالة على جهاز | ممكن | لا كعقد بيع | يحتاج قرار منتج إن كانت الكفالة الذهبية تباع لجهاز خارجي. |
| `golden_warranty_card_delivery` | بطاقة كفالة | ممكن إذا وجدت كفالة | لا كعقد بيع | يتبع وجود `device_warranty`، لا عقد البيع بحد ذاته. |
| `warranty_cancellation` | كفالة | ممكن إذا وجدت كفالة | لا كعقد بيع | يجب أن يستهدف `device_warranty` لا العقد. |
| `warranty_reactivation` | كفالة | ممكن إذا وجدت كفالة | لا كعقد بيع | يجب أن يستهدف `device_warranty` لا العقد. |

### 4.9.1 جرد تركيب وتشغيل الجهاز الخارجي حسب الحالة

هذا الجرد يثبت أن الجهاز الخارجي المؤهل لا يحتاج عقد بيع حتى يدخل مساري التركيب والتشغيل. الشرط الحاكم هو وجود `installed_devices.id` مع `customer_id` و`branch_id` وبيانات موقع قابلة للتخطيط، إضافة إلى سجل حيازة مفتوح للزبون في `device_possession_log`.

| حالة الجهاز الخارجي | `device_installation` | `device_activation` | الحكم |
|---|---:|---:|---|
| `delivered` | نعم | لا | الجهاز موجود عند الزبون وغير مركب؛ يجوز إنشاء مهمة تركيب فقط. |
| `installed` | لا | نعم | الجهاز مركب وغير مشغل؛ يجوز إنشاء مهمة تشغيل فقط. |
| `active` | لا | لا | الجهاز مشغل فعلا؛ لا تنشأ مهمة تركيب أو تشغيل جديدة، وتستخدم مسارات الفحص/الصيانة عند الحاجة. |
| `faulty` | لا | لا | الجهاز يحتاج فحصا أو صيانة قبل أي تركيب/تشغيل. |
| `out_of_service` | لا | لا | يحتاج مسار نقل/إرجاع/صيانة حسب القرار التشغيلي، وليس تركيباً أو تشغيلاً مباشراً. |
| `retrieved` / `in_workshop` / `ready` | لا | لا | الجهاز خارج موقع الزبون أو بعهدة الشركة؛ لا يبدأ تركيب/تشغيل قبل عودة علاقة موقع وحيازة واضحة. |

قواعد الإنشاء الناتجة:

- `device_installation` للجهاز الخارجي يعتمد على `device_id` وحالة `delivered`، ولا يشترط `contract_id`.
- `device_activation` للجهاز الخارجي يعتمد على `device_id` وحالة `installed`، ولا يشترط `contract_id`.
- `contractSnapshot = NULL` مقبول في هاتين المهمتين عندما يكون الجهاز خارجياً.
- `deviceSnapshot` إلزامي في المهمتين، ويجب أن يحتوي الحالة والموقع والزبون والفرع.
- لا يجوز استخدام عقد وهمي أو عقد بيع صوري لتجاوز غياب `contract_id`.

فجوة توثيق قبل التنفيذ: لا يوجد حالياً ملف تفصيلي مستقل لـ `device_installation` ضمن `docs/constitution/features/tasks`. قبل توسيع التنفيذ يجب إنشاء ملف `device-installation.md` أو اعتماد مرجع تفصيلي بديل يثبت شروط الإنشاء والنتائج والـ snapshots والـ cascading إلى `device_activation`.

### قرارات تنفيذية ناتجة

- أي زر أو API لإنشاء مهمة تشغيلية يجب أن يفحص `device.status` و`device.branch_id` و`device.customer_id` لا `contractId`.
- `contractSnapshot` قد يكون `NULL` وهذا طبيعي للجهاز الخارجي؛ لا يعد خطأ في المهمة.
- `deviceSnapshot` إلزامي للمهام التشغيلية المرتبطة بجهاز.
- مسارات التكاليف والإيصالات يجب أن تعرض العقد فقط إذا وجد، وأن تستخدم رقم المهمة والجهاز والزبون كأساس للجهاز الخارجي.

## 5. كيف تضيف نوع مهمة جديد؟

### 5.1 Frontend — ملف واحد

1. أنشئ: `packages/web/src/pages/tasks/XyzTaskDetail.tsx`
   - استورد `TaskDetailLayout`
   - عرّف `xyzExtension` (extraTabs, ResultRenderer, ...)
   - أضف `scheduleExtraRows` لو في بيانات جدولة خاصة
   - أضف `overviewIssuesFor` لو في تحققات خاصة

2. أضف Route في `App.tsx`:
   ```tsx
   <Route path="/tasks/xyz/:id" element={<XyzTaskDetail />} />
   ```

3. أضف رابط في قائمة نوع المهمة حيث تعرض الـ task card

### 5.2 Backend — لو المهمة تحتاج نتيجة خاصة

4. أضف endpoint في `openTasks.ts`:
   ```
   GET /:id/xyz-result    → إرجاع نتيجة محفوظة
   POST /:id/xyz-result   → حفظ نتيجة جديدة
   ```
   (استخدم نموذج `emergency-result` كمرجع)

5. أضف migration لجدول النتيجة لو احتجت:
   ```sql
   CREATE TABLE xyz_task_results (...)
   ```

### 5.3 ما لازم تتغيّر أبداً

- `TaskDetailLayout.tsx` — يعمل تلقائياً مع أي نوع جديد
- جميع التابات الأساسية — محملة تلقائياً
- دورة الحياة (11 حالة) — مشتركة لجميع الأنواع
- `task_type_config` — السجل موجود للـ 20 نوع
- `open_tasks` DB table — تقبل أي task_type

## 6. الخلاصة

الإضافة الجديدة تحتاج **ملف واحد في الـ Frontend** + **endpoint للنتيجة** لو في نتيجة خاصة. كل شيء آخر (التحميل، التابات الأساسية، سجل الأحداث، الجدولة، لقطة الزبون والعقد) يعمل تلقائياً من القالب.
