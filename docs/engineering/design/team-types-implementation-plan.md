# خطة تنفيذ أنواع الفرق (DEC-026)

> **الفرع:** `feat/team-types` (من `dev-next`)
> **التاريخ:** 2026-11-23
> **المرجع:** `docs/constitution/decisions/DEC-026-team-types.md`

## الحجم

جرد كامل للكود (2026-11-23) يبيّن حجم الأثر:

| الفئة | الملفات |
|---|---|
| قراءة أو كتابة `day_schedules.teams/solos` | 18 |
| بناء مفتاح `team_N`/`solo_N` أو تحليله | 21 |
| قراءة الأعضاء بأسماء الأدوار (`supervisor`، `technician`…) | 18، ومعها حوالي 36 قارئاً للقطة الفريق |
| أعمدة تخزّن مفتاح الفريق | 12 عموداً، منها `telemarketing_task_lists.id` = `tm_${date}_${teamKey}` |
| `roles.team_slot_type` | حوالي 30 |

## القرار التقني الأساسي: المفتاح يبقى بصيغته ويصبح صريحاً

بدل استبدال صيغة المفتاح في 12 عموداً (منها مفتاح أساسي، وقيدا CHECK بالتعبير `^(team|solo)_[0-9]+$`)، يُحفظ المفتاح **صريحاً داخل كل فريق** في الجدول:

| الحالة | المفتاح |
|---|---|
| فريق موجود اليوم | يحتفظ بمفتاحه الحالي (`team_0`، `solo_1`). فلا تتغير أي بيانات مرتبطة به |
| فريق جديد | `team_<n>`، حيث `n` أكبر رقم مستخدم في ذلك اليوم + 1. لا يُعاد استخدام رقم أبداً |

المفتاح يبقى متوافقاً مع كل التعبيرات والقيود الحالية، لكنه لم يعد رقماً في المصفوفة: البحث عن الفريق يكون بالمفتاح، وحذف فريق لا يزيح الباقين. ونوع الفريق يُقرأ من `teamTypeId` لا من البادئة `solo_`.

### الشكل الجديد لجدول اليوم

```json
{
  "teams": [
    { "key": "team_0", "teamTypeId": 1, "members": { "supervisor": [12], "technician": [18], "telemarketers": [22, 23] } },
    { "key": "solo_0", "teamTypeId": 2, "members": { "technician": [31] } },
    { "key": "team_2", "teamTypeId": 5, "members": { "collector": [40], "slot_a1b2c3d4": [41] } }
  ],
  "solos": []
}
```

`members` مفاتيحه هي `slot_key` من خانات النوع. وعمود `solos` يبقى فارغاً للتوافق، ثم يُحذف لاحقاً.

## المراحل

| المرحلة | المحتوى | الحالة |
|---|---|---|
| **1. الكتالوج** | هجرة 505 (الجداول والبذرة والصلاحية)، وخدمة وواجهة API لأنواع الفرق واختيار الفرع، مع اختبارات | ✅ `d4f9dd4` |
| **2. نموذج الجدول** | هجرة 506 تحوّل `teams/solos` إلى الشكل الجديد. ووحدة مركزية `daySchedule.ts` لكل القراءات (الفريق بمفتاحه، والرئيس، والميدانيون، والمسوقون، والمالكون، ونوع الفريق). وتحويل القرّاء الـ 18 إليها، ومعها دالة SQL `task_team_label`. السلوك يبقى مطابقاً للنوعين الحاليين | ✅ `27d960b`. مقارنة القديم بالجديد على `golden_crm_srv` (داخل ROLLBACK): 35 فريقاً في 24 يوماً، 0 فروق |
| **3. القدرة** | فلترة المهام بأنواع المهام المسموحة لنوع الفريق في الاستعلامات الثلاثة. وشرط «كل مهام الحبيبة» (D6)، واستثناء الطارئة بالاتجاهين (D7)، وعدّاد «زبائن لا يقدر فريقك عليهم» | ✅ `75adbc2`. قاعدة واحدة `teamCapability.ts` يطبّقها العدّ ونطاق العمل (ومنه التوليد والداشبورد)، والطارئة مستثناة في فحص الحبيبة. النوعان الأوليان: 0 فروق على 35 فريقاً |
| **4. الواجهات** | شاشة إدارة أنواع الفرق، واختيار أنواع الفرع، وشاشة الجدولة ديناميكية حسب خانات كل نوع، وتحديث خطة اليوم وتوزيع المسارات ونافذة إعادة الإسناد | 🟡 الشاشات منجزة: `/admin/team-types` (الكتالوج، بصلاحية `planning.team_types.manage`)، و«أنواع فرق الفرع» داخل جدولة الفرق، والجدولة الديناميكية (المرحلة 2). بقي تعميم إعادة إسناد فريق الزيارة للأنواع المخصصة (انظر البقايا) |
| **5. المشاركة والفجوة** | تنبيه المشاركة في توزيع المسارات (D8)، والمطالبة بالحبيبة كاملة عند دخولها كشف اتصال (الشرط الثاني في PL-R009) | |
| **6. الدستور** | تحديث `planning.md` و`day-schedules.md` وPL-R009 وR011 وR014، وتغيير حالة DEC-026 بقرار صاحب المنتج | |

## بقايا معروفة من المرحلة 2 (تدخل في المرحلة 4)

| البند | الوضع الحالي |
|---|---|
| إعادة إسناد فريق الزيارة (DEC-020) | ما زالت بالأدوار الثلاثة (مشرف، فني، متدرب) وأعمدة `reassigned_*`. تعمل للنوعين الأوليين، أما النوع المخصص فيحتاج تعميماً |
| دالة SQL `field_visit_member_ids` | تقرأ حقول اللقطة القديمة، فالخانات الميدانية الإضافية في نوع مخصص لا تدخل فحص «مشغول في نفس الوقت» على مستوى القاعدة. أما فحص التطبيق (`teamSnapshotMemberIds`) فيقرأ `fieldEmployeeIds` |
| تسميات الفرق في بعض شاشات الويب | `PlanningContactTargets` و`ReassignTeamModal` و`TeamTasksDetail` تستنتج التسمية من المفتاح. تبقى صحيحة لأن صيغة المفتاح لم تتغير، لكنها لا تعرض اسم النوع المخصص |
| `roles.team_slot_type` | لم يعد يقرّر الجدولة. ما زال للجلسة وسياسة جهاز الويب والتقارير |

## مبادئ التنفيذ

| المبدأ | التطبيق |
|---|---|
| لا تغيير سلوك قبل المرحلة 3 | المرحلة 2 إعادة هيكلة فقط: النوعان الأوليان يتصرفان كما اليوم بالضبط |
| لقطة الفريق متوافقة | تبقى حقول `supervisorEmployeeId` و`technicianEmployeeId`… في `team_snapshot` (يقرؤها حوالي 36 ملفاً)، وتضاف إليها `teamTypeId` و`members` |
| الهجرات على `golden_crm_srv` | تُجرَّب داخل transaction مع ROLLBACK، ولا تُطبَّق فعلياً إلا بإذن |
| `team_slot_type` | يبقى للجلسة وسياسة جهاز الويب والتقارير إلى أن تنتقل تدريجياً |
