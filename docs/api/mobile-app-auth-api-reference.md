# مرجع API — مصادقة تطبيق الزبائن (Customer App Auth)

> **الحالة:** مرجع رسمي · **الإصدار:** 1.0 · **الفرع:** `Authenticate` · **القرار الحاكم:** `DEC-013`
> **المرجع الحيّ (Swagger):** `{BASE}/api-docs` — الوسوم `App - Auth` و`App - Account`.

هذا مرجعٌ تقنيّ لكل نقطة نهاية (endpoint) خاصة بمصادقة تطبيق الزبائن، مع تعريف كامل لكل بارامتر ونوع بياناته وقيوده. لا يشرح التدفقات؛ لتسلسل الاستخدام راجع دليل التكامل.

---

## 1. الاصطلاحات العامة

| البند | القيمة |
|---|---|
| الرابط الأساسي `{BASE}` | `http://localhost:3000` (تطوير) — `https://<production-host>` (إنتاج) |
| بادئة كل المسارات | `{BASE}/api/app` |
| ترميز الطلب/الاستجابة | `application/json` (UTF-8) |
| ترويسة المصادقة (النداءات المحمية) | `Authorization: Bearer <accessToken>` |

### 1.1 أنواع البيانات المستخدمة

| النوع | الوصف |
|---|---|
| `string` | سلسلة نصية UTF-8 |
| `integer` | عدد صحيح 64-bit |
| `number` | عدد عشري (float) |
| `boolean` | `true` / `false` |
| `uuid` | سلسلة نصية بصيغة UUID v4، مثل `6f0a…-…-…` |
| `timestamp` | سلسلة نصية بصيغة ISO-8601 UTC، مثل `2026-07-19T10:20:30.000Z` |
| `object` | كائن JSON |
| `enum(...)` | سلسلة نصية من مجموعة قيم محدّدة |
| `T \| null` | النوع `T` أو `null` (اختياري يقبل الفراغ) |

### 1.2 قيمٌ معدودة (Enumerations)

| الاسم | القيم |
|---|---|
| `Purpose` | `account_creation` · `login` · `account_deletion` · `request_status` · `service_request` |
| `MobileStatus` | `visitor` · `pending` · `active` · `suspended` |
| `TokenType` | `Bearer` |

### 1.3 كائن الخطأ الموحّد

كل استجابة غير ناجحة (`>= 400`) تُعيد الشكل التالي:

| الحقل | النوع | الوصف |
|---|---|---|
| `error` | `string` | رسالة عربية موجّهة للعرض |
| `details` | `object \| null` | حقول سياقية إضافية حسب الحالة (اختياري) |
| `details.code` | `string` | الرمز الآلي — **افرِّع عليه، لا على نص الرسالة** |

> **تغيّر منذ 2026-07-31 (جولة التحصين الأولى):** الخطأ الداخلي غير المتوقّع لم يعد يُعيد نصّه الأصلي. كل `500` تعيد الآن رسالة عربية عامة ثابتة («تعذّر إتمام العملية. حاول لاحقاً.») مع `details.code = "internal_error"`؛ والتفصيل يبقى في سجلّ الخادم تحت الوسم `[app:<الموقع>]`. إن كان التطبيق يعرض `error` مباشرةً فالسلوك تحسّن تلقائياً، وإن كان يحلّل نصّه فتوقّف عن ذلك.

### 1.4 أكواد الحالة (HTTP)

| الكود | الدلالة |
|---|---|
| `200` | نجاح |
| `400` | مدخل غير صالح |
| `401` | مصادقة مفقودة/منتهية — يلزم تجديد التوكن |
| `403` | ممنوع (حساب موقوف) — `details.code = "suspended"` |
| `404` | غير موجود |
| `409` | تعارض (حالة مانعة) |
| `413` | الحمولة تجاوزت السقف المسموح |
| `429` | تجاوز الحد (نافذة إرسال / محاولات / حدّ معدّل / سقف يومي) |
| `500` | خطأ خادم — رسالة عامة ثابتة، `details.code = "internal_error"` |
| `503` | خدمة غير متاحة مؤقتاً (سجلّ الأنواع) |

## 2. OTP

### 2.1 `POST /api/app/otp/send`

إرسال رمز تحقّق لمرة واحدة. **عام (بلا مصادقة).**

**جسم الطلب (Body):**

| البارامتر | النوع | إلزامي | الوصف / القيود |
|---|---|:--:|---|
| `phone` | `string` | ✅ | رقم موبايل سوري. يُطبَّع في الخادم (يقبل `09XXXXXXXX`، `9639…`، `009639…`). الصيغة الصالحة نهائياً `^09\d{8}$`. |
| `purpose` | `enum(Purpose)` | ✅ | غرض الرمز. أغراض الحساب تُشتقّ من `GET /api/app/account/status` (القسم 5)؛ أما إرسال طلب خدمة كزائر فيستخدم `service_request`. |

**شروط الغرض:** يُفحص الشرط **قبل** توليد الرمز وإرساله، فلا تُستهلك رسالة على رحلة لا يمكن أن تنجح. `login` و`account_deletion` يشترطان حساباً مفعّلاً؛ و`request_status` يشترط طلباً معلّقاً **أو مرفوضاً غير مؤرشف**؛ و`account_creation` يرفض وجود حساب مفعّل أو موقوف (الموقوف يُعاد تفعيله إدارياً ولا يُستبدل) **ويرفض وجود طلب معلّق** (صاحب الطلب المعلّق بعد إعادة التنزيل غرضه الصحيح `request_status`)؛ و`service_request` متاح للزائر ولا يشترط حساباً.

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `sent` | `boolean` | دائماً `true` عند النجاح. |
| `expiresInSeconds` | `integer` | عمر صلاحية الرمز بالثواني (افتراضي `120`). |
| `resendInSeconds` | `integer` | المدة قبل السماح بإعادة الإرسال (افتراضي `60`). |
| `devCode` | `string` | **بيئة التطوير فقط** — الرمز نصّاً لتسهيل الاختبار. غير موجود في الإنتاج. |

**الأخطاء:**

| الكود | `details` | الحالة |
|---|---|---|
| `400` | — | رقم أو غرض غير صالح. |
| `403` | `{ code: "suspended" }` | الحساب موقوف (`login` / `account_deletion`). |
| `404` | `{ code: "no_active_account" }` | لا حساب مفعّل للرقم (`login` / `account_deletion`). |
| `404` | `{ code: "no_pending_request" }` | لا طلب معلّق للرقم (`request_status`). |
| `409` | `{ code: "active_account_exists" \| "suspended" \| "pending_request_exists", status }` | `account_creation` لرقمٍ له حساب حيّ (مفعّل أو موقوف) أو طلب قيد المراجعة. |
| `429` | `{ retryAfterSeconds: integer }` | لم تنقضِ نافذة إعادة الإرسال (60 ثانية). |
| `429` | `{ code: "daily_cap_reached", limit, windowHours: 24 }` | **جديد** — تجاوز الرقم سقفه اليومي من رسائل التحقق عبر **كل** الأغراض مجتمعةً (10 افتراضياً). لا تُعد المحاولة اليوم. |
| `429` | `{ code: "rate_limited", retryAfterSeconds }` | **جديد** — حدّ معدّل الطلبات لعنوان العميل (5 نداءات / 10 دقائق على `send`). راجع §6.1. |

> **الطلب المرفوض لا يحجب:** بعد رفض طلب يستطيع المستخدم إرسال `account_creation` جديد بحرية — قاعدة «طلب مفتوح واحد» تخصّ المعلّق فقط. مصير الطلب المرفوض وسببه يُعرَضان بلا حجب لصاحب الرقم عبر `account/status?ref=` (§3.1) أو `…/mine` (§3.2.2).

### 2.2 `POST /api/app/otp/verify`

التحقّق من الرمز؛ عند النجاح يُصدر `handle` (إثبات لمرة واحدة). **عام.**

**جسم الطلب:**

| البارامتر | النوع | إلزامي | الوصف / القيود |
|---|---|:--:|---|
| `phone` | `string` | ✅ | نفس الرقم المُرسَل إليه الرمز. |
| `code` | `string` | ✅ | الرمز المُدخَل. |
| `purpose` | `enum(Purpose)` | ✅ | يجب أن يطابق غرض `send`. |

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `verified` | `boolean` | دائماً `true`. |
| `handle` | `uuid` | مُعرّف التحقّق. صالح ~10 دقائق، يُستهلَك مرة واحدة، يُرفَق بالخطوة التالية. |
| `purpose` | `enum(Purpose)` | صدى الغرض. |

**الأخطاء:**

| الكود | `details` | الحالة |
|---|---|---|
| `400` | `{ attemptsRemaining: integer }` | رمز غير صحيح (مع المتبقّي). |
| `400` | — | لا يوجد رمز فعّال / انتهت صلاحيته. |
| `429` | — | تجاوز حدّ المحاولات (5). |

## 3. الحساب (Account)

### 3.1 `GET /api/app/account/status`

الوضع المحسوب لرقمٍ ما. **عام.**

**بارامترات الاستعلام (Query):**

| البارامتر | النوع | إلزامي | الوصف |
|---|---|:--:|---|
| `phone` | `string` | ✅ | رقم الموبايل (يُطبَّع). |
| `ref` | `string` | ❌ | رقم مرجع الطلب (`publicRefNumber`) المخزَّن محلياً من ردّ الإنشاء. مفتاح الإفصاح عن الرفض (أدناه). |

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `status` | `enum(MobileStatus)` | `visitor` / `pending` / `active` / `suspended`. |
| `rejection` | `object \| null` | **فقط** عند تمرير `ref` مطابق لطلبٍ مرفوض غير مؤرشف لنفس الرقم: `{ code, label, rejectedAt }` — نفس أكواد `/mine` (القسم 3.2.2) و`label` عربي جاهز للعرض. |

**الإفصاح عن الرفض بلا OTP:** رقم المرجع لا يملكه إلا مُرسِل الطلب (يُعاد مرة واحدة في ردّ الإنشاء)، فتمريره مع الرقم يثبت أن السائل هو صاحب الطلب — فيصله المصير والسبب **في نفس نداء الإقلاع** دون أي دورة OTP. من يملك الرقم وحده يرى `visitor` صامتاً كما كان. الإفصاح **سببٌ فقط، لا بيانات شخصية** — اللقطة الكاملة تبقى خلف `/mine` المحكوم بـ OTP. وأرشفة الطلب المرفوض من لوحة التحكم تُغلق النافذة.

**الأخطاء:** `400` — رقم مفقود أو غير صالح.

### 3.2 `POST /api/app/account-requests`

إنشاء طلب حساب لزائر. **مصادقة: `handle`** (بغرض `account_creation`).

**جسم الطلب:**

| البارامتر | النوع | إلزامي | الوصف / القيود |
|---|---|:--:|---|
| `handle` | `uuid` | ✅ | ناتج `verify`. يجب أن يكون مُتحقَّقاً وغير مُستهلَك وضمن نافذته الزمنية. |
| `form` | `object` | ✅ | بيانات النموذج (أدناه). |

**كائن `form`:**

| الحقل | النوع | إلزامي | الوصف / القيود |
|---|---|:--:|---|
| `firstName` | `string` | ✅ | الاسم الأول (غير فارغ). |
| `fatherName` | `string` | ✅ | اسم الأب (غير فارغ). |
| `lastName` | `string` | ✅ | الكنية (غير فارغة). |
| `primaryMobile` | `string` | ✅ | رقم الموبايل الرئيسي. **يجب أن يطابق** رقم الـ `handle` المُتحقَّق. |
| `primaryMobileHasWhatsapp` | `boolean` | ✅ | هل الرقم الرئيسي متاح عليه واتساب. يقبل Boolean حقيقياً فقط. |
| `secondaryMobile` | `string \| null` | ❌ | رقم ثانوي (يُطبَّع ويُتحقّق منه إن وُجد، ويجب أن يختلف عن الرئيسي). |
| `secondaryMobileHasWhatsapp` | `boolean` | شرطي | إلزامي عند وجود `secondaryMobile`؛ ولا يجوز أن يكون `true` من دون رقم ثانوي. |
| `governorate` | `integer` | ✅ | معرّف وحدة جغرافية من **المستوى 1** (`geo_units.id`). يُنتقى عبر `GET /api/public/areas` (القسم 3.2.1). النص الحر مرفوض (`400`). |
| `cityOrArea` | `integer \| null` | ❌ | معرّف **مستوى 2**؛ إن وُجد فأبوه هو `governorate`. |
| `subArea` | `integer \| null` | ❌ | معرّف **مستوى 3**؛ إن وُجد فـ `cityOrArea` إلزامي وأبوه هو `cityOrArea`. |
| `neighborhood` | `integer \| null` | ❌ | معرّف **مستوى 4**؛ إن وُجد فـ `subArea` إلزامي وأبوه هو `subArea`. |
| `detailedAddress` | `string` | ✅ | العنوان التفصيلي (غير فارغ). |
| `notes` | `string \| null` | ❌ | ملاحظات حرة. |
| `location` | `object \| null` | ❌ | إحداثيات: `{ lat: number, lng: number }`. |

**استجابة `200`:** يُعاد **اللقطة المخزَّنة كاملةً** — بنفس شكل `POST /api/app/account-requests/mine` بالضبط (القسم 3.2.2).

| الحقل | النوع | الوصف |
|---|---|---|
| `status` | `string` | دائماً `"pending"`. |
| `requestId` | `integer` | معرّف الطلب الداخلي. |
| `publicRefNumber` | `string` | مرجع عام بصيغة `SR-YYYYMMDD-NNNN`. |
| `submittedAt` | `timestamp` | تاريخ الإرسال. |
| `firstName`, `fatherName`, `lastName` | `string \| null` | الاسم كما خُزِّن (مشذّباً). |
| `primaryMobile`, `secondaryMobile` | `string \| null` | الأرقام **مطبَّعة** (`09XXXXXXXX`). |
| `primaryMobileHasWhatsapp`, `secondaryMobileHasWhatsapp` | `boolean \| null` | حالة واتساب لكل رقم كما خُزّنت في الطلب؛ `null` فقط للسجلات التاريخية التي سبقت هذه الحقول. |
| `address` | `object` | `{ governorate, cityOrArea, subArea, neighborhood, detailedAddress }` — **أسماءً** لا معرّفات. |
| `notes` | `string \| null` | الملاحظات. |
| `location` | `object \| null` | `{ lat, lng }` إن أُرسلت. |

> **لماذا اللقطة كاملة:** النموذج يُرسل معرّفات `geo_units` رقمية، فلو أُعيد المعرّف وحده لاضطرّ التطبيق لتتبّع أسماء المنتقي بنفسه ليعرض «دمشق / كفرسوسة / جمالة». وبإعادة ما خُزِّن فعلاً **بعد التطبيع**، تُرسم شاشة «قيد المراجعة» بلا نداء إضافي، ولا ينشأ فرق بين ما يراه الزبون وما يراه الأدمن، ويكفي **راسمٌ واحد** في التطبيق لمساري الإنشاء والاستعادة. خزّن الردّ محلياً كما هو.

**الأخطاء:**

| الكود | `details` | الحالة |
|---|---|---|
| `400` | — | `handle` غير صالح / الرقم لا يطابق / حقل إلزامي ناقص / **عنوان غير صالح** (معرّف غير رقمي، مستوى غير مطابق، سلسلة آباء غير متّسقة، أو وحدة غير موجودة). |
| `409` | `{ status: "active" }` | الرقم مرتبط بحساب مفعّل. |
| `409` | `{ status: "pending" }` | يوجد طلب معلّق لنفس الرقم. |

**ملاحظة العنوان:** يُخزَّن العنوان بمعرّفاته الرقمية القانونية إضافةً إلى **لقطة أسماء** (`labels`) وقت الإرسال، فتظهر الأسماء جاهزةً للأدمن للمقارنة دون استعلام إضافي.

### 3.2.1 `GET /api/public/areas` — قوائم المستويات الإدارية (اختيار العنوان)

مسار **عام** (بلا توكن) يُغذّي القوائم المتتالية لاختيار العنوان في نموذج إنشاء الحساب. يُستدعى بالتتالي: بلا وسيط يعيد المحافظات (مستوى 1)، ومع `parent_id` يعيد أبناء الوحدة (المستوى التالي).

**بارامترات الاستعلام:**

| البارامتر | النوع | إلزامي | الوصف / القيود |
|---|---|:--:|---|
| `parent_id` | `integer` | ❌ | معرّف الوحدة الأب. حذفه يعيد محافظات المستوى 1. |
| `activeOnly` | `boolean` | ❌ | بارامتر توافق قديم؛ النتائج العامة أصبحت دائماً محصورة بالوحدات المفعّلة. |

**استجابة `200`:** مصفوفة عناصر —

| الحقل | النوع | الوصف |
|---|---|---|
| `id` | `integer` | معرّف الوحدة (يُرسَل في الفورم). |
| `name` | `string` | اسم الوحدة للعرض. |
| `type` | `enum` | `governorate` / `city` / `sub_area` / `neighborhood`. |
| `parentId` | `integer \| null` | معرّف الأب. |

**تدفّق الاختيار المتتالي:** `GET /api/public/areas` (المحافظة) ← `?parent_id={gov}` (المنطقة) ← `?parent_id={city}` (الناحية) ← `?parent_id={sub}` (الحي). يُرسَل معرّف كل مستوى مُختار في `form`.

**البحث الذكي:** `GET /api/public/areas/search?q={query}&limit=15`، حيث `q` بين حرفين و80 حرفاً و`limit` بين 1 و20. تعيد الاستجابة `{ items }`؛ كل عنصر يحوي `id`, `name`, `level`, `type`, `parentId` ومصفوفة `path` المرتبة من المحافظة إلى النتيجة. لا تُعاد نتيجة إذا كانت وحدتها أو أي أب في مسارها معطّلاً، ويستطيع التطبيق تحويل `path` مباشرةً إلى اختيار المستويات الأربعة.

### 3.2.2 `POST /api/app/account-requests/mine` — استعادة طلب معلّق أو مرفوض

يعيد الطلب **كما أرسله الزبون** ليُعاد بناء شاشة «قيد المراجعة» بعد فقدان النسخة المحلية (إعادة تنزيل التطبيق أو تغيير الجهاز). **مصادقة: `handle`** (بغرض `request_status`)، ويُستهلك هنا.

وإن كان أحدث طلب غير مؤرشف **مرفوضاً**، يعيد اللقطة ذاتها بـ `status: "rejected"` مع كائن `rejection` (الكود + نصّ عربي + التاريخ). هذا الإفصاح **للمالك المُثبَت حصراً** — المسار العام `account/status` يبقى يجيب `visitor` ولا يكشف الرفض ولا سببه. أرشفة الطلب من لوحة التحكم تُغلق نافذة الإفصاح. والطلب المعلّق الحيّ يغلب دائماً طلباً مرفوضاً أقدم.

البيانات شخصية (اسم + عنوان سكن)، لذلك **لا تُعاد عبر `GET /api/app/account/status`** — المسار العام مفتاحه رقم هاتف، وإعادتها هناك تحوّله إلى دليل بحث عكسي. إثبات ملكية الرقم شرط، وهو الـ `handle`.

**جسم الطلب:**

| البارامتر | النوع | إلزامي | الوصف |
|---|---|:--:|---|
| `phone` | `string` | ✅ | الرقم المستهدف؛ يجب أن يطابق رقم الـ `handle`. |
| `handle` | `uuid` | ✅ | ناتج `verify` بغرض `request_status`. |

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `status` | `enum(pending, rejected)` | حالة أحدث طلب غير مؤرشف. |
| `rejection` | `object \| null` | **عند `rejected` فقط**: `{ code, label, rejectedAt }`. الأكواد: `duplicate` / `invalid_request` / `spam` / `out_of_scope` / `unverified_caller` / `device_not_company`، و`label` نصّ عربي جاهز للعرض. |
| `requestId` | `integer` | معرّف الطلب. |
| `publicRefNumber` | `string` | مرجع عام `SR-YYYYMMDD-NNNN`. |
| `submittedAt` | `timestamp` | تاريخ الإرسال. |
| `firstName`, `fatherName`, `lastName` | `string \| null` | الاسم كما أُرسل. |
| `primaryMobile` | `string` | الرقم الرئيسي (مطبَّع). |
| `primaryMobileHasWhatsapp` | `boolean \| null` | حالة واتساب للرقم الرئيسي؛ `null` لطلب تاريخي لم يخزّنها. |
| `secondaryMobile` | `string \| null` | الرقم الثانوي. |
| `secondaryMobileHasWhatsapp` | `boolean \| null` | حالة واتساب للرقم الثانوي؛ `false` عند عدمه في الطلب الجديد، و`null` لطلب تاريخي لم يخزّنها. |
| `address` | `object` | `{ governorate, cityOrArea, subArea, neighborhood, detailedAddress }` — **أسماءً** من لقطة الطلب. |
| `notes` | `string \| null` | الملاحظات. |
| `location` | `object \| null` | `{ lat, lng }` إن أُرسلت. |

**الأخطاء:** `400` (handle غير معروف / غير مُتحقَّق / منتهٍ / الرقم لا يطابق)، `404` مع `code = "no_pending_request"` (لا طلب معلّقاً ولا مرفوضاً غير مؤرشف)، `409` (handle مُستهلَك).

> **مصدر البيانات:** لقطة `submitted_payload` غير القابلة للتعديل — أي ما كتبه المستخدم، لا سجل الزبون. بعد اعتماد الأدمن تنتقل الشاشة إلى `GET /api/app/me` وقد **تختلف القيم** لأن مصدرها حينئذٍ سجل `clients`. ابنِ الشاشة بحقل مصدر (`request` / `account`).

### 3.2.3 `POST /api/app/service-requests` — إرسال طلب خدمة

نقطة الدخول الموحدة لطلبات تطبيق الموبايل. لا تكفي إضافة صف في `service_request_type_config`: يقبل الخادم النوع فقط عند اجتماع تعريف Registry فعّال يسمح بالموبايل وهوية المرسل ونمط الإرسال، ومعالج كود مثبت، وتطابق `formVersion` بينهما. يدعم التنفيذ الأول `requestType = "water_check"`، وتُضاف الأنواع الأخرى دون إنشاء مسار مصادقة جديد.

- **الزائر:** لا يرسل Bearer، ويتحقق أولاً بـ OTP ذي الغرض `service_request` ثم يرسل `handle` لمرة واحدة داخل الجسم. في `for_self` يجب أن يطابق رقم المستفيد الرقم المتحقق منه؛ وفي `for_another` يمثل الرقم المتحقق منه مقدم الطلب بينما تبقى بيانات المستفيد مستقلة.
- **الزبون المسجّل:** يرسل `Authorization: Bearer ...`، ولا يحتاج `handle`. الخادم يشتق `app_account` و`client` والرقم من التوكن وقاعدة البيانات، ولا يقبل حقول الجسم كمصدر لهوية المرسل.
- إذا وُجدت ترويسة Authorization غير صالحة أو منتهية أو لحساب موقوف يُرفض الطلب؛ لا يحدث سقوط صامت إلى مسار الزائر.
- لا يُخزَّن `handle` ضمن `submitted_payload`. تُحفظ بيانات النموذج كلقطة، وتُحفظ هوية المرسل في روابط مستقلة.

الحد الأدنى للجسم: `requestType`, `submissionMode`, `firstName`, `lastName`, `phoneNumber`, `governorateId`, `detailedAddress`، إضافةً إلى `handle` للزائر فقط. الاستجابة `201` تعيد `id`, `publicRefNumber`, `status`, `requesterAuth`, ونتيجة حل الفرع.

الأخطاء المغلقة المهمة: `unknown_request_type`، `request_type_inactive`، `request_type_not_implemented`، `request_type_not_available_on_mobile`، `request_type_not_available_for_requester`، `unsupported_submission_mode`، `unsupported_form_version`، و`request_type_configuration_mismatch`.

> **هذا المسار له مرجع مستقل ومفصّل:** `docs/api/mobile-service-requests-api-reference.md` — يضم قائمة حقول النموذج الكاملة بحدودها، وجدول الأخطاء الكامل، وتغييرات جولة التحصين الأولى (نموذج مغلق يرفض الحقول غير المعلَنة، وقاعدة الطلب المفتوح الواحد، و`id` صار عدداً لا نصّاً). **إن كان لديك بناء عامل، اقرأ قسم 6 هناك أولاً: فيه تغييران كاسران للتوافق.**

### 3.2.4 `GET /api/app/service-requests/types`

يعيد الأنواع القابلة للإرسال فعليًا من الموبايل، أي تقاطع Registry الحي مع المعالجات المثبتة والمتوافقة. لا يعيد نوعًا لمجرد أن صفه `is_active = true`. يحتوي كل عنصر: `requestType`, `labelAr`, `descriptionAr`, `formVersion`, `formSource`, `submitterTiers`, و`submissionModes`.

### 3.2.5 كتالوج أجهزة الشركة العام

مسارا الكتالوج عامّان للزائر ولا يحتاجان توكنًا أو OTP:

| العملية | المسار | الاستجابة |
|---|---|---|
| قائمة الأجهزة المنشورة | `GET /api/app/catalog/devices` | `{ items: PublicDeviceListItem[], total, page, limit }` |
| تفاصيل جهاز منشور | `GET /api/app/catalog/devices/:deviceId` | `PublicDeviceDetails` |
| قائمة الفروع المنشورة | `GET /api/app/catalog/branches` | `{ items: PublicBranchListItem[] }` |
| تفاصيل فرع منشور | `GET /api/app/catalog/branches/:branchId` | `PublicBranchDetails` |

القائمة مصفّحة خادمياً: تقبل `page` (الافتراضي `1`) و`limit` (الافتراضي `12`، والأقصى `50`) إضافةً إلى `featured=true|false` و`category` و`search` (حتى 100 محرف). تقبل أيضاً `fields=names` للمنتقيات الخفيفة؛ عندها يحوي كل عنصر فقط `id`, `nameAr`, `nameEn`، بينما حذف `fields` أو إرسال `fields=full` يعيد بطاقة الكتالوج الكاملة. `items` تمثل الصفحة المطلوبة فقط؛ وعلى التطبيق تصفير النتائج والعودة إلى الصفحة الأولى عند تغيير أي فلتر. كلا المسارين يعيدان فقط `device_models` التي تحقق `is_active = true` و`deleted_at IS NULL`؛ لذلك يعيد مسار التفاصيل `404` للجهاز غير الموجود أو غير الفعال أو المحذوف.

بيانات العرض العامة تشمل الاسمين العربي والإنكليزي، ورمز الموديل `code`، والتصنيف والوصف والصورة الأساسية والوسائط وفترات الصيانة والكفالات، إضافةً إلى `services` بالقيم العامة المعتمدة: `تسليم`، `تركيب`، `صيانة`، `تعليم`. تضيف استجابة القائمة `goldenWarrantyAvailable` لبيان دعم موديل الجهاز للكفالة الذهبية، و`activeDiscount` الاختياري بالشكل `{ label, percentage, validUntil }` للخصم الفعال حالياً بتوقيت دمشق، أو `null` عند عدم وجود خصم. وتضيف استجابة التفاصيل مزايا الشراء، وفروع البيع المعتمدة، والإكسسوارات الفعالة المتوافقة، وملفات الكاتلوك العامة. يبقى اسم التخزين الداخلي `supportedVisitTypes` غير مكشوف، ولا يعيد المساران السعر أو علاقات الأقسام.

المراجع الرسمية الكاملة المخصصة لمطور الموبايل:

- `docs/api/mobile-device-catalog-api-reference.md`
- `docs/api/mobile-branch-catalog-api-reference.md`

### 3.5 `GET /api/app/me`

ملف الزبون المسجّل دخوله عن نفسه، مُحلّاً من سجل الزبون المرتبط. **مصادقة: `Bearer`.** مُقلَّل البيانات — الحقول الداخلية لا تُعرَض.

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `appAccountId` | `integer` | معرّف حساب التطبيق. |
| `accountStatus` | `string` | `"active"`. |
| `memberSince` | `timestamp` | تاريخ إنشاء الحساب. |
| `firstName` | `string \| null` | الاسم الأول. |
| `fatherName` | `string \| null` | اسم الأب. |
| `lastName` | `string \| null` | الكنية. |
| `primaryMobile` | `string` | رقم الدخول (مطبَّع). |
| `primaryMobileHasWhatsapp` | `boolean` | حالة واتساب للرقم الرئيسي من `clients.contacts`. |
| `secondaryMobile` | `string \| null` | أول رقم ثانوي فعّال مختلف عن الرئيسي. |
| `secondaryMobileHasWhatsapp` | `boolean` | حالة واتساب للرقم الثانوي المُعاد. |
| `secondaryMobiles` | `string[]` | أرقام إضافية من `contacts` (مطبَّعة، بلا تكرار، وبلا الرقم الرئيسي). |
| `classification` | `enum(OP, FOP, Lead)` | تصنيف السجل. `OP`/`FOP` حالتا ترقية؛ وكل ما عداهما `Lead` افتراضاً. **لا يكون `null` أبداً.** |
| `address` | `object` | العنوان بالأسماء — للعرض (أدناه). |
| `addressIds` | `object` | نفس المستويات بمعرّفات `geo_units` — للمنتقي (أدناه). |
| `geoUnitId` | `integer \| null` | أعمق مستوى متوفّر. |

**كائن `address` (أسماء للعرض):**

| الحقل | النوع | الوصف |
|---|---|---|
| `governorate` | `string \| null` | اسم المحافظة (مستوى 1). |
| `cityOrArea` | `string \| null` | اسم المنطقة (مستوى 2). |
| `subArea` | `string \| null` | اسم الناحية (مستوى 3). |
| `neighborhood` | `string \| null` | اسم الحي (مستوى 4). |
| `detailedAddress` | `string \| null` | العنوان التفصيلي النصّي. |

**كائن `addressIds` (معرّفات — أُضيف 2026-08-02):**

| الحقل | النوع | يقابل في استمارة الطلب |
|---|---|---|
| `governorate` | `integer \| null` | `governorate` (ويُقبل `governorateId`) |
| `cityOrArea` | `integer \| null` | `cityOrArea` (ويُقبل `regionId`) |
| `subArea` | `integer \| null` | `subArea` (ويُقبل `subdistrictId`) |
| `neighborhood` | `integer \| null` | `neighborhood` (ويُقبل `neighborhoodId`) |

استعمل `addressIds` لضبط المنتقي التتالي مسبقاً، ثم مرّرها كما هي إلى
`POST /api/app/service-requests` حسب جدول المقابلة أعلاه. **لا تطابق بالأسماء**:
الأسماء تتكرّر بين المحافظات، وإعادة تسمية وحدة تُبطل المطابقة صامتةً.

السلسلة **مضمونة الاتّصال دائماً** (لا فجوة بين مستوى وما فوقه)، لأنها تُبنى
بالصعود في شجرة المناطق من أعمق وحدة مخزَّنة لا بقراءة أعمدة سجلّ الزبون —
وتلك الأعمدة قد تكون ناقصة. لذلك يقبلها مدقّق العنوان دائماً.

**العنوان التفصيلي غالباً `null`** — أكثر السجلات لا تحمله. اترك الحقل فارغاً
ليملأه المستخدم، ولا تعتبر ذلك خطأً.

**الأخطاء:** `401` (توكن)، `403` مع `details.code = "suspended"`، `404` (لا حساب/سجل).

> الأجهزة والعقود والطلبات ميزات تطبيق منفصلة (خارج نطاق المصادقة)، تُبنى لاحقاً بنفس النمط المصادَق.

## 4. الجلسة والتوكنات (Auth)

نموذج التوكنات: `accessToken` قصير (JWT، ~60 دقيقة) + `refreshToken` طويل دوّار (~60 يوماً). عند كل `refresh` يُصدر `refreshToken` جديد ويُبطَل القديم.

### 4.1 `POST /api/app/auth/login`

مبادلة `handle` (بغرض `login`) بتوكنات لحساب مفعّل. **مصادقة: `handle`.**

**جسم الطلب:**

| البارامتر | النوع | إلزامي | الوصف |
|---|---|:--:|---|
| `handle` | `uuid` | ✅ | ناتج `verify` بغرض `login`. |
| `deviceLabel` | `string \| null` | ❌ | وسمٌ للجهاز يُخزَّن مع رمز التجديد. |

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `accessToken` | `string` | JWT قصير الأجل. |
| `refreshToken` | `string` | رمز تجديد مبهم (دوّار). |
| `tokenType` | `enum(TokenType)` | `"Bearer"`. |
| `expiresIn` | `integer` | عمر الـ `accessToken` بالثواني. |
| `account` | `object` | `{ appAccountId: integer, clientId: integer, phone: string }`. |

**الأخطاء:** `400`؛ `404` مع `details.code = "no_active_account"`.

### 4.2 `GET /api/app/session`

تمهيد الجلسة عند الفتح؛ يُعيد قراءة حالة الحساب (يلتقط الإيقاف). **مصادقة: `Bearer`.**

**استجابة `200`:**

| الحقل | النوع | الوصف |
|---|---|---|
| `status` | `string` | `"active"`. |
| `account` | `object` | `{ appAccountId: integer, clientId: integer, phone: string }`. |

**الأخطاء:** `401` (توكن مفقود/غير صالح/منتهٍ)؛ `403` مع `details.code = "suspended"`.

---

### 4.3 `POST /api/app/auth/refresh`

تدوير التوكنات. **مصادقة: `refreshToken` في الجسم.**

**جسم الطلب:**

| البارامتر | النوع | إلزامي | الوصف |
|---|---|:--:|---|
| `refreshToken` | `string` | ✅ | رمز التجديد الحالي. |

**استجابة `200`:** بنية مطابقة لـ `login` (`accessToken`, `refreshToken`, `tokenType`, `expiresIn`, `account`).

**الأخطاء:**

| الكود | `details.code` | الحالة |
|---|---|---|
| `400` | — | الرمز مفقود. |
| `401` | — | رمز غير صالح أو منتهٍ. |
| `401` | `session_ended` | أُبطِل بالخروج/الإيقاف → سجّل الدخول من جديد. |
| `401` | `token_reused` | إعادة استخدام رمز مُدوَّر (اشتباه) → أُلغيت العائلة. |
| `403` | `suspended` | الحساب موقوف. |

إبطال عائلة رمز التجديد. **مصادقة: `refreshToken` في الجسم.**

**جسم الطلب:**

|---|---|:--:|---|
| `refreshToken` | `string` | ✅ | رمز التجديد الحالي. |

## 5. تدفّق الإقلاع (Boot flow)

القرار عند فتح التطبيق **مدخله التخزين المحلي لا حالة الحساب** — فالحالة مجهولة قبل النداء. ثلاثة فروع حصرية لا تلتقي:

| المخزَّن محلياً | النداء عند الإقلاع | ثم |
|---|---|---|
| `refreshToken` | `GET /api/app/session` | `200` → وضع الزبون · `401` → `refresh` ثم إعادة المحاولة مرة واحدة · `403 suspended` → وضع الإيقاف |
| رقم فقط (بلا توكن) | `GET /api/app/account/status?phone=` | التوجيه بالقيم الأربع (أدناه) |
| لا شيء | **لا نداء** | زائر — التطبيق يعمل كاملاً، ويُطلب الرقم فقط عند فتح الملف الشخصي |

فشل الـ `refresh` (`session_ended` / `token_reused`) يمسح التوكنين ويُسقط المستخدم إلى الفرع الثاني.

`GET /api/app/me` **ليس** نداء إقلاع: يُستدعى عند فتح صفحة الملف الشخصي فقط، لأنه يحلّ شجرة `geo_units` ويقرأ سجل الزبون. وفحص الجلسة الدوري وظيفة `GET /api/app/session` الخفيف.

### 5.1 التوجيه من `status` — واختيار غرض الـ OTP

**`status` يحدّد غرض الرمز، لا نيّة المستخدم.** المستخدم بعد إعادة التنزيل يقصد «تسجيل الدخول» وهو في الحقيقة صاحب طلب معلّق؛ فلو أُرسل الرمز بغرض `login` لنجح كل شيء حتى `login` ثم فشل بـ `404`.

| `status` | الشاشة | غرض الـ OTP |
|---|---|---|
| `visitor` | زر إنشاء حساب | `account_creation` |
| `pending` | بطاقة «قيد المراجعة» | `request_status` (عند الحاجة لاستعادة التفاصيل) |
| `active` | زر تسجيل الدخول | `login` |
| `suspended` | شاشة الإيقاف | — |

حالة خاصة واحدة تخرج عن الجدول: `visitor` **مع لقطة محلية لطلب سابق** تعني أن الطلب حُسم — والسبب يصل تلقائياً في ردّ `status` نفسه عند تمرير `ref` (§3.1، بلا OTP). ويبقى غرض `request_status` مسموحاً للمرفوض غير المؤرشف أيضاً، لمن فقد لقطته المحلية ويريد استعادتها كاملة عبر `…/mine` (§5.2).

### 5.2 حالة `pending` — مصدر بيانات الشاشة

المسار الطبيعي **محلي بالكامل**: ردّ `POST /api/app/account-requests` هو اللقطة كاملةً، فيُخزَّن **كما هو** وتُرسم الشاشة منه فوراً بلا شبكة ولا حاجة لتتبّع أسماء المنتقي. والرقم يُخزَّن معه لأنه مفتاح فرع الإقلاع الثاني، و`publicRefNumber` لأنه مفتاح الإفصاح عن الرفض في `status` (§3.1).

**قاعدة نداء الإقلاع للمعلّق**: ما دامت لقطة محلية موجودة، يُستدعى `status` دائماً **مع `ref`**: `GET /api/app/account/status?phone=…&ref=SR-…` — فإن حُسم الطلب رفضاً وصل السبب في نفس الردّ تلقائياً، بلا OTP وبلا نداء إضافي.

وعند فقدان النسخة المحلية: `status` يعيد `pending` → «أكّد رقمك لعرض تفاصيل طلبك» → OTP بغرض `request_status` → `POST /api/app/account-requests/mine` → تُعرض الشاشة كاملة **وتُخزَّن محلياً من جديد** فلا يتكرّر الطلب.

عند كل فتح للصفحة يُعاد فحص `status` (مع `ref`): بقاؤه `pending` يُبقي البطاقة، وتحوّله إلى `active` يعني الموافقة (اعرض «سجّل دخولك»). أمّا الرفض فيصل **تلقائياً في نفس الردّ**: `status: "visitor"` مع كائن `rejection` — اعرض بطاقة «لم يُستكمل طلبك» بسببها (`rejection.label` جاهز للعرض) + زر «التقديم من جديد» (يمسح النسخة المحلية ويعيد نموذج الإنشاء — الرفض لا يمنع التقديم مجدداً). لا OTP في هذا المسار إطلاقاً.

وإن عاد `visitor` **بلا** `rejection` رغم تمرير `ref` صحيح، فالطلب أُرشف — امسح النسخة المحلية واعرض زر الإنشاء برسالة محايدة. ويبقى مسار OTP بغرض `request_status` ثم `…/mine` متاحاً كخيار ثانٍ: يعيد للمرفوض غير المؤرشف اللقطة الكاملة مع `rejection` — يلزم فقط عند فقدان اللقطة المحلية.

### 6.1 حدود معدّل الطلبات (منذ 2026-07-31)

طبقتان مستقلّتان تعملان معاً. الأولى **لكل عنوان عميل** ومسار، والثانية **لكل هوية** (رقم أو حساب) محفوظة في قاعدة البيانات فلا يوسّعها إعادة التشغيل ولا تعدّد العمليات.

| المسار | الحدّ | النافذة |
|---|---|---|
| `POST /api/app/otp/send` | 5 | 10 دقائق |
| `POST /api/app/otp/verify` | 20 | 10 دقائق |
| `POST /api/app/service-requests` | 10 | ساعة |
| بقية `POST` على `/api/app` (دخول، تجديد، خروج، إنشاء حساب، حذف) | 30 | 10 دقائق |
| كل `GET` على `/api/app` و`/api/public` | 120 | دقيقة |

الرد عند التجاوز `429` مع ترويسة `Retry-After` و`details = { code: "rate_limited", retryAfterSeconds }`.

وعلى مستوى الهوية: 10 رسائل تحقق لرقم واحد خلال 24 ساعة عبر كل الأغراض (`daily_cap_reached`)، وطلب فحص مياه مفتوح واحد لرقم المستفيد (`open_request_exists`)، و5 طلبات فحص مياه من هوية واحدة خلال 24 ساعة (`daily_request_quota_reached`).

### 6.2 قاعدة التعامل مع `429`

لا تُعِد المحاولة تلقائياً قبل انقضاء `retryAfterSeconds` — إعادة المحاولة الفورية تجدّد الحظر ولا تنجح. وميّز في رسالة المستخدم بين ثلاث حالات: `rate_limited` مؤقتة بالثواني، و`daily_cap_reached` سقف رسائل يومي («حاول غداً»)، و`daily_request_quota_reached` سقف طلبات يومي («حاول غداً»). القيم كلها قابلة للضبط بمتغيّرات بيئة، فلا تُضمّنها في التطبيق — اقرأها من الرد.
